# Changelog

## Unreleased

- **Pictures reach every model that takes them**: OpenAI and Gemini as well as Clef. Until now only Clef was sent a picture, and the other models judged one line saying a picture was there.
- **A PDF is sent as the file to a model that reads PDFs** (Gemini). The text it is sent names the file instead of repeating its text layer; every other model is given the text layer as before. Checked live with a PDF that has a text layer and with a scan that has none.
- **A scanned PDF is no longer refused** as empty evidence. A model that reads PDFs reads it; any other model is told there was no text to show.
- `verdict run --models` says what each model was sent: a **pictures sent** and a **PDFs sent** column appear when the cases carry them (`1/1`, or `0/2` for a model given text instead), and `--json` has the counts as `media`. Ratings record `raw.documents` beside `raw.images`.
- **A run from the command line waits out a provider's rate limit.** On HTTP 429 a decision provider is asked again after the wait it names (its `Retry-After` header, or a "retry in 35s" in its answer), up to four more times, before the case fails. A run of 100 pictures on Gemini's free tier, which allows 50,000 input tokens a minute, lost 57 cases without this and none with it. The engine does it only when given `rateLimitWait`, which the CLI gives; a server does not hold a request open, and a queued evaluation is still retried by its queue.
- `examples/receipts`: a hundred receipt photos from a public dataset put to the four models that take pictures, with the question about the number of items written three times and the run of each.
- Not built yet: turning a PDF's pages into pictures for the models that take only pictures.

## 0.3.6

- **`verdict run --models` shows the probability each model gave its answer** beside the answer, where it showed the provider's `confidence`. The confidences were not comparable: for an answer of probability `p` among `n` options Gemini reports `p`, Jev and OpenAI report `(p − 1/n) / (1 − 1/n)`, and Clef reports `(Σp² − 1/n) / (1 − 1/n)`, so one message read 0.62, 0.54 and 0.28 for probabilities of 0.62, 0.60 and 0.48. `--json` now carries `probability` next to `confidence` for every answer. A score that falls between two levels has no probability and shows no number.
- The banking example called that number a probability when it was a confidence. Its table and saved output now show probabilities, from the same stored run.

## 0.3.5

- **Gemini's decision model is a sixth provider**: `--models gemini`, or `provider: gemini` in a rubric, asks `gemini-decision-1` through Google's Decisions API with `GEMINI_API_KEY` (or `GOOGLE_API_KEY`). Checked against the live service on 2026-11-12; `docs/PROVIDERS.md` shows the request and a verbatim answer. Text only for now.
- `examples/banking77` is run on six models. The five from before agree with the labels on the same number of cases; Gemini agrees on 68 of 80, and the models still differ on the same ten cases.

## 0.3.3

- **Node 22 or newer is required** (22.12 for the CLI). The packages said Node 20, but that had stopped being true: the PDF reader they depended on (`unpdf` 2.1) declared Node 24, so every install on Node 20 or 22 printed an `EBADENGINE` warning, and on Node 20 reading a PDF failed with "Iterator is not defined". Node 20 itself reached end of life in April 2026. `unpdf` is now 1.9, which runs on Node 22, so an install on Node 22 or 24 is quiet. On an older Node the CLI and the MCP server say so in one sentence and stop, instead of failing later inside a dependency.
- A workflow lists the MCP server in the official MCP registry after a release (`.github/workflows/mcp-registry.yml`, run by hand).

## 0.3.0

- One rubric, several decision models: `verdict run -r <rubric> -d <cases> --models jev,clef,clef-flash` runs the rubric once per model without editing it and shows the models side by side — agreement with your labels, failures, tokens, calls and time per model, then every case the models answered differently, with the expected label where there is one. A model is an alias (`jev`, `jev-preview`, `clef`, `clef-flash`) or `provider:model`. Only decision judges are re-pointed; each run is of a version that differs only in its binding and is kept for `verdict diff`. A model that could not answer keeps its row with the reason and is left out of the disagreements. `--json` prints the comparison. Core: `compareModels`, `answerLabel`, `criterionAnswer`. Checked live with Jev, Clef and Clef-flash (2026-11-11); `examples/models` is the rubric and cases of that run.
- Use a rubric your team's server keeps from any machine, by name instead of by file. `verdict run`, `diff`, `eval`, `check` and `compare` take `-r <name> --env <environment>` (the version that environment runs), `-r <name>@latest` (the newest uploaded) and `-r <name>@rv_…`. The document is frozen locally and used only when it freezes to the id the server named, then kept in the local data directory, so a version already there needs neither sign-in nor network. Judging stays on the machine, with its own model keys. A bare name without `--env` or `@…` means what it always did.
- `verdict pull <name> --env <environment>` (or `<name>@latest`, `<name>@rv_…`) writes a version from a project into a rubric file that freezes to the same id, and records the version and its name in `verdict.lock`. `verdict pull hub:…` is unchanged.
- `verdict push <file>` freezes the file and records it in `verdict.lock` before uploading, so sharing a rubric takes one command and `verdict promote <file>` works straight after it. It no longer warns that a name given with `--name` could not be recorded.
- SDK: `environments.get(project, name, { include: "rubrics" })` returns each pointer's rubric document.
- Spelling: the CLI's help and messages say "organization". Option, variable and header names are unchanged (`--org`, `VERDICT_ORG`, `x-verdict-org`).

## 0.2.0

- Control plane: which rubric version each environment runs. Projects, environments, immutable rubric versions, pointers and their history under `/v1/projects` (route group `control`; `createApp({ routes })` and `VERDICT_ROUTES` choose which groups a server offers). An uploaded version is frozen again and must match its id; a promotion applies all of its changes or none, only from the versions the caller saw (a stale one answers 409 with where the pointers are), and a rollback undoes a pointer's latest change. New `ControlStore` (`store.control`) on the Memory, File and Drizzle stores, with SQLite/D1 and Postgres migrations; every read and write is scoped to a tenant and a project.
- Management commands in the CLI: `verdict project`, `env` (`list`, `show`, `history`, `unset`), `push`, `promote` and `rollback`. `promote` takes a rubric file only when it freezes to the version `verdict.lock` records, shows the change, asks, and sends it with the versions it showed. The project, server and organisation come from the option, the environment (`VERDICT_PROJECT`, `VERDICT_API_URL`, `VERDICT_ORG`), then the nearest committed `verdict.yaml`.
- `verdict login` signs in to a server: it shows a code to approve in the browser and saves the key the server issues, one key per server address; it refuses a sign-in route that points away from the server it was asked to sign in to. `verdict login --with-key` saves an operator-issued key from standard input for self-hosted servers.
- Run and comparison reports: `verdict report`, `run --report`, `diff --report`, the `actions/diff` GitHub Action and `reports.*` in the SDK send a run's conditions, counts, agreement and usage, or a comparison's kind and class counts, to a project (a `policy_change` comparison, re-scored from recorded answers, is reported like any other). The request shapes have no field for a case, an input or an output, so the server never receives one. A CI key's report may bring its rubric version along.
- Services read what their environment runs: `GET /v1/projects/:project/environments/:environment?include=rubrics` returns every pointer with its document in one answer, with an ETag derived from the pointers (an unchanged environment answers 304). SDK `verdict.environment({ project, environment })` holds the answer, asks again on the first call after `refreshMs` without a timer (it works in Workers), uses a document only if it freezes locally to the id the server named, and carries on with what it holds, marked `stale`, when the server does not answer; `fallback` covers a cold start. `examples/control-plane` walks the whole loop without a model key, against its own server or one that is already running.
- Seams for servers with people and plans, unchanged for a server built from this repository alone: `auth` receives the request and may return who is asking and `claims`; every control route asks `authorize(action, target)` before it reads or writes, and a refusal may carry details (for example which limit was reached) in the error object. The request may name an organisation (`x-verdict-org`; SDK `org`, CLI `--org`). `ControlStore.usage` counts what a tenant keeps in one call. Retention keeps the latest change of every pointer however old, so an environment can always be rolled back.
- `verdict publish --run` sends only the run's numbers: cases not published in the same request are sent as random stand-ins, where before the request carried their names, labels and evaluation ids (the hub stored none of them).
- `verdict diff` re-scores instead of re-running when the head differs from the base only in policy (threshold, choice values, weights, aggregation, low-confidence handling): the base run's recorded answers are replayed through the engine under the head's rules, with no judge calls, and the comparison is called a **policy change** (new `ComparisonKind` `policy_change`). It falls back to a real run, saying why, when answers cannot be replayed (other questions or models, panels or non-decision judges, checks, a missing answer). Core: `rescoreRunUnder`, `policyRescoreBlocker`; runs record `rescoredFrom`. `--rerun` still asks the judges.
- Fix: on Cloudflare Workers no decision provider was registered, so every decision judge (Jev by default) failed with `unknown decision provider`. Packages are marked `"sideEffects": false` and the built-in providers were registered by a side-effect-only import, which esbuild (wrangler) drops; registration is now an explicit call, and a test rejects side-effect-only imports in side-effect-free packages. Found in a local `wrangler dev` + D1 rehearsal of the hub, now described in the deploy guide.
- Hub pages and `hub_get` lead a reported run with its agreement on the card's question (cards are labelled per question, so the overall pass/fail tally was 0 of 0).
- Hub operations. Operators take publications down with a public reason and restore them (`/v1/admin/publications`, `…/:id/takedown`, `…/:id/restore`; an author's own withdrawal cannot be undone by operators); public reads of a taken-down version answer 410 `taken_down`. Sign-in, publishing (previews included) and public reads are rate-limited (10 / 30 / 300 a minute by default; 429 with `Retry-After`), in memory or through Cloudflare's rate limiting bindings (`HUB_LOGIN_LIMITER`, `HUB_PUBLISH_LIMITER`, `HUB_READ_LIMITER`); `AppOptions.limits` and `clientKey` configure them. `/v1/admin/*` no longer needs a database key store unless managing keys. MCP tools `hub_search`, `hub_get` and `fork_rubric` (`VERDICT_HUB_URL`); a forked card is stored as a rubric with `metadata.forkedFrom`.
- Public hub reads. `GET /v1/public/rubrics` (search; one result per card at its newest live version), `GET /v1/public/rubrics/:owner/:slug` (a card at a version, with its history; 410 for a withdrawn version) and `GET /v1/public/publications/:id`, with no key; they read only publications and never return the publishing tenant. HTML pages at `/hub` and `/hub/:owner/:slug` (no scripts, strict CSP) show the question, lineage, author-reported runs, public cases, versions and copyable commands. `verdict pull hub:owner/slug[@rv_…]` copies a card exactly with its public cases and `verdict fork hub:…` starts a version from it; both check locally that the rubric freezes to the version the hub names and record the origin and licence in `verdict.lock`. SDK `hub.search`, `hub.card`, `hub.publication`. Hub commands no longer fall back to `VERDICT_API_KEY` when they have no hub key.
- Hub sign-in and publishing from the CLI. `verdict hub login` runs GitHub's device flow and trades the token for a hub key (`POST /v1/hub/login`; the token is verified with GitHub — against the OAuth app when `GITHUB_CLIENT_SECRET` is set — and never stored); `hub whoami`, `hub list`, `hub logout` (revokes the key). `verdict publish` sends one version, only the cases named with `--case` (marked public) and the numbers of runs named with `--run`, shows the hub's preview and asks before publishing; `verdict withdraw`. With `GITHUB_CLIENT_ID` set, only signed-in GitHub accounts publish, under their login, and a ref stays with the account that first published it. New `publishers` table (SQLite/D1 and Postgres migrations); SDK `hub.*`.

- Publishing to the public hub (first part): `POST /v1/publications/preview`, `POST /v1/publications`, `GET /v1/publications`, `DELETE /v1/publications/:id` and `publications.*` in the SDK. A publication copies one rubric version, the cases marked public and the numbers of chosen runs; it is checked (one criterion, licence, yes/no threshold, no judge `baseUrl`, public cases with text/json/url inputs, runs of the same version only) and the preview returns exactly the document that would be stored. New `publications` table (SQLite/D1 and Postgres migrations) and `PublicationStore` on the Memory, File and Drizzle stores. Public read pages, GitHub sign-in and `verdict publish` follow.

- `verdict eval`, `check` and `compare` check rubric files listed in `verdict.lock`: a file that no longer freezes to its locked version, questions that differ from the locked run's, or a provider now naming another model behind the same alias produce a warning, or a failure with `--strict` (a changed file fails before any judge is called). `verdict diff --markdown` prints a PR-comment-ready comparison. New `actions/diff` GitHub Action: compares a rubric changed in a pull request with its base-branch version on the same gold cases, keeps one comment per rubric up to date, writes the job summary and fails on chosen case classes.

- `verdict watch` has a comparison screen at `/compare`: pick two stored runs and a label set; it says first whether the difference is the rubric's alone, shows the rubric diff folded around the changes with the fork lineage, and lists cases regressions-first with expected labels, input previews and both answer distributions. `verdict diff` prints its link.

- CLI: `verdict version freeze|show|list|export|verify`, `verdict fork`, `verdict run`, `verdict diff` and `verdict rescore` on the local engine, with `verdict.lock` recording each rubric file's version, its fork parent and the questions and models of its last run. `diff` reuses stored runs of the same version and inputs, re-scores against `--labels` without judge calls, and gates CI with `--fail-on`; `version verify` fails when a committed rubric no longer matches the lock.

- Rubric versions, dataset versions, runs and run comparison in `@verdict-ai/core` (`freezeRubric`, `forkDraft`, `changeKinds`, `createDatasetVersion`, `runCases`, `rescoreRun`, `compareRuns`). Versions have content-derived ids and separate judgment, policy, binding and metadata hashes; runs record the questions sent and the models that answered; comparisons separate fixes from regressions, refuse to attribute results to a rubric change when anything else differed, and flag answers that moved close to flipping. `MemoryStore` and `FileStore` persist them (`VersionStore`). CLI commands follow.

- Rubrics may declare `inputSchema`, a JSON Schema subset that every `json` input must satisfy. A mismatch fails the evaluation before ingestion or any judge call, with `inputErrors` (`{ input, path, message }`) on the evaluation; it is not retried. `verdict check` and `check_against_humans` count such cases as `invalidInput`. Unsupported schema keywords are rejected when the rubric is parsed.

- Binary criteria take an optional `threshold`: the P(true) at or above which a decision model's noul answer counts as true (default 0.5, unchanged). The derived noul confidence is now the margin from that threshold (still `|2p − 1|` at 0.5), and ratings record `raw.threshold` and `raw.thresholdSource`.
- Decision ratings keep the requested model and the model the provider's response named apart: `raw.requestedModel`, `raw.resolvedModel`, `raw.modelVerified`. Before, a response without a model id was recorded as if the requested alias (`jev-latest`) had answered; `raw.model` keeps its earlier meaning.
- `verdict check` / `check_against_humans`: choice criteria are compared by option id (previously not compared), and calibration pairs choice decisions with the human majority option. Gold cases accept `id`, `expected` (alias of `human.criteria`), `labelSource`, `split`, `visibility`, `kind` and `note`; reports add per-split agreement and label-source counts; labels the rubric cannot read are rejected before any judge runs.

- `verdict watch`: a live local page over stored evaluations. Single evaluations show score, gates, criteria and changed lines; batches show a leaderboard with each subject's score per round and its rank change. Evaluations of one batch now share a `batchId` (engine, REST, SDK).
- Vision inputs: `image` inputs (PNG/JPEG/WebP) and `url` inputs with `screenshot` reach vision-capable decision models (Clef, through the REST API or the Workers AI binding) as embedded images, within Clef's limits. Text-only providers never receive them. Stored evaluations keep image metadata only. CLI: image paths become image inputs, `eval --screenshot`; Node API server: `VERDICT_SCREENSHOTS=1`.
- Check a rubric against people: `verdict check -r rubric.yaml -g gold.jsonl` and the MCP `check_against_humans` tool run a rubric over subjects humans already judged and report agreement overall and per criterion, how many subjects low-confidence escalation handed to a human, and each disagreement.

## 0.1.0

First public release of the `@verdict-ai/*` packages: `core` (rubrics, judges, aggregation, calibration), `db` (Drizzle stores for D1/SQLite and Postgres), `api` (Hono REST for Workers and Node), `cli`, `mcp` and `sdk`.

- Decision-model judges (TypeSafe Jev, Cloudflare Clef and Clef-flash) as the default, with human, benchmark, LLM and panel judges.
- Rubrics with numeric, binary, ordinal and choice criteria, pre-screen checks, and two-layer aggregation including safe formulas.
- Confidence gates with escalation, idempotency keys, an async queue with retries, and tenant-scoped storage.
- Inputs: text, JSON, files (PDF, DOCX, Markdown), web pages and YouTube transcripts.

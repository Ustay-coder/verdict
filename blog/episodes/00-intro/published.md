> 코드 품질을 두 가지 점수로 나누어 계량화하기 시작한 이유, 그 점수를 통해 코드를 개선하게 된 방향을 스토리로 담았습니다. 

## "코드가 지저분하긴 한데, 어떤 기준으로 정리하지?" 

스타트업에서 AI로 코드를 짜게 되면, 기능 추가와 UI 업데이트에 치이다보니 코드 정리가 뒷전이 됩니다. "언젠가는 코드를 정리해야 하는데..." 라는 압박을 받습니다. 하지만 이 또한 코드를 정리하는 기준이 없고, 그 기준에 맞게 코드 품질을 판가름하기 위한 시간이 부족하죠. 

그래서 코드 품질을 계량화 하기로 했습니다. Verdict 평가 엔진에 Jev, Clef 등의 Decision Model을 붙인 뒤 기준에 따른 점수를 매기면, AI가 어느 파트에서 코드를 정리하고 개선해야 하는지, 그리고 고친 뒤에 정말 나아졌는지를 쉽게 답할 수 있기 때문입니다.

## 점수는 두 가지로 나눴습니다

코드 품질 평가를 위해, 평가 엔진 [Verdict](https://github.com/Ustay-coder/verdict)에 루브릭 두 개를 올려 사용했습니다. 

| 루브릭 | 단위 | 판단 기준 |
|---|---|---|
| 파일 루브릭 | 파일 1개 | 10개 기준을 각각 0~5점으로 채점해 100점 만점으로 환산합니다. 판정은 판정 모델 Clef가 합니다. |
| repo 루브릭 | 저장소 전체 | 커버리지, 중복, 복잡도, 보안 등 지표 9종을 수식으로 종합해 100점 만점으로 환산합니다. 모델은 개입하지 않습니다. |

파일 루브릭의 10개 기준은 
- testability, 
- analysability, 
- dead_code, 
- error_handling, 
- file_length, 
- cohesion, 
- types, 
- naming, 
- comments, 
- unchecked_casts

입니다.

둘을 나눈 이유는 서로 못 보는 것이 다르기 때문입니다. 
파일 루브릭은 "이 파일이 읽고 테스트하기 쉬운가"를, 
repo 루브릭은 "저장소 전체가 얼마나 테스트되고 중복되는가"를 봅니다. 

파일 하나하나는 깔끔해도 저장소 전체의 테스트가 비어 있을 수 있는데, 파일 루브릭만으로는 그 상태를 확인하기 어렵습니다.

Verdict는 이런 루브릭을 모델이든 수식이든 판정기에 맡겨 채점하고 집계하는 도구입니다. 이 도구로 우리 코드를 채점했습니다. 

## 코드 품질 기준선을 측정했습니다.

2026-11-07에 측정한 기준선은 이랬습니다.

- 측정 대상 파일은 2,515개, 파일 루브릭 평균 84.23점
- 평균은 나빠 보이지 않았지만 D등급(70점 미만) 파일이 108개
- 파일을 줄 수로 가중하면 평균은 78.77점으로 내려감. 큰 파일일수록 점수가 낮다는 뜻. 
- 기준별로 가장 약한 항목은 comments(3.91), testability(4.14), analysability(4.19)였고, 모두 5점 만점입니다.
- repo 루브릭 종합은 44.1점으로 D등급이었습니다.

점수가 낮은 파일은 유형 세개에 몰려 있었습니다. 
- 인증, 검증, DB 접근, 응답 조립이 함수 하나에 섞인 API route, 
- 상태와 API 호출과 업무 규칙이 한 파일에 있는 클라이언트 훅,
- 800줄에서 1,500줄에 이르는 서비스와 repository

전체 평균만 봤다면 이 세 유형이 눈에 띄지 않았을 것입니다. 파일 단위 점수를 줄 수로 가중해 보고 나서야 큰 파일에 문제가 몰려 있다는 것이 보였습니다.

## 첫 주의 결과

2026-11-14에 같은 루브릭으로 다시 측정했습니다.

| 지표 | 기준선 | 현재 | 변화 |
|---|---:|---:|---:|
| 파일 루브릭 평균 | 84.23 | 85.52 | +1.29 |
| 줄 수 가중 평균 | 78.77 | 81.12 | +2.35 |
| 400줄 초과 파일 | 69 | 41 | -28 |
| 커버리지(line) | 60.2% | 65.6% | +5.4 |
| repo 루브릭 종합 | 44.1 | 49.2 | +5.1 |

D등급 파일은 108개에서 72개로, 중복률은 4.73%에서 3.81%로 줄었습니다.

이 표를 읽을 때 알아 둘 것이 세 가지 있습니다.

- **다시 채점한 파일은 아직 723개입니다.** 
기준선 이후 바뀌었거나 새로 생긴 파일만 다시 판정했고, 나머지는 기준선 점수를 그대로 썼습니다. 판정 모델의 점수는 실행마다 조금 달라질 수 있어서, 기준선과 같게 파일당 한 번만 판정했습니다.
- **줄 수에 대한 가중 평균이 더 올렸습니다.** 
단순 평균은 1.29점, 가중 평균은 2.35점 올랐습니다. 낮은 점수를 받은 대용량 파일을 작은 파일 여럿으로 나누면 그것만으로도 가중 평균은 오릅니다. 큰 파일의 영향이 줄었다는 것까지는 말할 수 있지만, 그중 얼마가 실제 품질 향상이고 얼마가 분할 효과인지는 이 숫자로 가를 수 없습니다.

## 아직 모자란 것

- repo 루브릭 종합은 여전히 D등급입니다. 
- 파일을 나누면 파일 수가 늘어납니다. 측정 대상이 2,515개에서 3,138개로 늘어났습니다. 

## 이 시리즈에서 다룰 것

측정이 끝날 때마다 한두 편씩 이어서 씁니다.

1. 기준선 들여다보기: 2,515개 파일을 채점해 보니 파악한 것 
2. 파일럿: 루브릭으로 API route와 훅을 나누는 패턴
3. 점수 낮은 API route를 핸들러로 분리하기
4. 거대 서비스와 repository를 쪼개고, 파일이 늘어나는 대가를 치른 이야기
5. 한 배치가 점수를 깎은 실패 기록
6. 측정을 믿을 수 있는가: 판정 분산과 커버리지 예외

다음 글은 기준선을 더 자세히 보고, 어떤 기준이 왜 약했는지, 코드 품질 평가 점수에서 줄 수에 대해 더 가중치를 왜 더 주었는지 설명합니다.

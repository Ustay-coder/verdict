# 00-intro 아웃라인

**한 줄 약속**: 코드 품질을 "느낌"이 아니라 두 개의 점수로 재면, 무엇부터 고칠지가 보입니다.

**핵심 주장**: 점수는 개선을 증명하는 용도이기 전에 *우선순위를 정하는* 도구다. 첫 주 기록이 그 예다.

## 목차
1. 문제: "코드가 지저분하다"는 말로는 다음 행동이 정해지지 않는다
2. 두 개의 루브릭 — 파일 루브릭(10개 기준), repo 루브릭(지표 9종)
3. 첫 측정에서 보인 것 — 기준선 요약 (summary.*, file_rubric.low_score_types)
4. 첫 주의 결과 — 스코어보드 (summary.*)  <!-- viz:scoreboard -->
5. 아직 모자란 것 — repo 종합 D, 보안, 측정의 한계 (measurement_caveats)
6. 시리즈 로드맵과 다음 편 예고

## 사용 수치 키
summary.*, file_rubric.criteria_count, file_rubric.weakest_baseline, repo_rubric.metric_count, measurement_caveats.judge_variance

## 반드시 밝힐 것
- 판정 모델 점수는 실행마다 조금 달라질 수 있고 파일당 1회만 판정했다.
- repo 루브릭 종합은 여전히 D등급이고 보안 항목은 0점이다.
- 파일 수 증가(2,515 → 3,138)는 큰 파일을 나눈 결과라 평균 비교 시 모집단이 다르다.

없음(첫 편).

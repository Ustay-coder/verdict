> 이 글을 읽으면 코드 품질을 두 가지 점수로 나누어 재는 방법과, 그 점수가 첫 일주일 동안 우리에게 무엇을 알려 줬는지 알게 됩니다.

## "코드가 지저분하다"로는 다음 행동이 정해지지 않습니다

리팩터링 회의는 대개 비슷하게 흘러갑니다. 누군가 이 부분이 너무 복잡하다고 말하고, 다른 사람이 그래도 돌아가니 놔두자고 답합니다. 어느 쪽도 틀리지 않았지만, 회의가 끝나도 무엇을 먼저 고칠지는 정해지지 않습니다.

그래서 우리는 코드 품질을 점수로 재기로 했습니다. 점수가 정답을 알려 주지는 않습니다. 다만 "어디가 가장 나쁜가"와 "고친 뒤 정말 나아졌는가"라는 두 질문에는 숫자로 답할 수 있습니다.

## 점수는 두 가지로 나눴습니다

평가 엔진 Verdict에 루브릭 두 개를 올렸습니다.

| 루브릭 | 단위 | 무엇을 보는가 |
|---|---|---|
| 파일 루브릭 | 파일 1개 | testability, analysability, naming 등 10개 기준을 각각 0~5점으로 채점해 100점 만점으로 환산합니다. 판정은 모델이 합니다. |
| repo 루브릭 | 저장소 전체 | 커버리지, 중복, 복잡도, 보안 등 지표 9종을 수식으로 종합해 100점 만점으로 환산합니다. 모델이 개입하지 않습니다. |

둘을 나눈 이유는 서로 못 보는 것이 다르기 때문입니다. 파일 루브릭은 "이 파일이 읽기 쉬운가"를 보고, repo 루브릭은 "저장소 전체가 얼마나 테스트되고 중복되었는가"를 봅니다. 하나만 있었다면 파일 하나는 깔끔한데 저장소는 테스트가 비어 있는 상황을 놓쳤을 겁니다.

## 기준선에서 보인 것

2026-11-07에 측정한 기준선은 이랬습니다.

- 측정 대상 파일은 2,515개였고, 파일 루브릭 평균은 84.23점이었습니다.
- 평균은 나쁘지 않아 보였지만 D등급(70점 미만) 파일이 108개 있었습니다.
- 파일을 줄 수로 가중하면 평균이 78.77점으로 내려갑니다. 큰 파일일수록 점수가 낮다는 뜻입니다.
- 기준별로 가장 약한 항목은 comments(3.91), testability(4.14), analysability(4.19)였고, 모두 5점 만점입니다.
- repo 루브릭 종합은 44.1점으로 D등급이었습니다.

점수가 낮은 파일은 세 유형에 몰려 있었습니다. 인증, 검증, DB 접근, 응답 조립이 함수 하나에 섞인 API route, 상태와 API 호출과 업무 규칙이 한 파일에 있는 클라이언트 훅, 그리고 800줄에서 1,500줄에 이르는 서비스와 repository입니다. 평균 하나로는 이 세 유형이 보이지 않았을 겁니다.

## 첫 주의 결과

2026-11-14에 같은 방법으로 다시 측정했습니다.

| 지표 | 기준선 | 현재 | 변화 |
|---|---:|---:|---:|
| 파일 루브릭 평균 | 84.23 | 85.52 | +1.29 |
| 줄 수 가중 평균 | 78.77 | 81.12 | +2.35 |
| D등급 파일 | 108 | 72 | -36 |
| 400줄 초과 파일 | 69 | 41 | -28 |
| 커버리지(line) | 60.2% | 65.6% | +5.4 |
| 중복률 | 4.73% | 3.81% | -0.92 |
| repo 루브릭 종합 | 44.1 | 49.2 | +5.1 |

단순 평균은 1.29점 올랐지만 줄 수 가중 평균은 2.35점 올랐습니다. 큰 파일부터 고쳤다는 것이 숫자에도 드러납니다.

## 아직 모자란 것

좋은 소식만 있지는 않습니다.

- repo 루브릭 종합은 여전히 D등급입니다. 의존성 보안 항목은 아직 손대지 않아 0점입니다.
- 파일을 나누면 파일 수가 늘어납니다. 측정 대상이 2,515개에서 3,138개로 늘었으니, 두 평균은 완전히 같은 모집단의 비교가 아닙니다.
- 판정 모델의 점수는 실행마다 조금 달라질 수 있습니다. 기준선과 같게 파일당 한 번만 판정했습니다.

이 한계들은 앞으로의 글에서 따로 다룹니다.

## 앞으로 쓸 글

# 01-baseline 아웃라인

**한 줄 약속**: 평균 84.23점짜리 코드베이스에서 실제로 약한 곳이 어디였는지, 그리고 그걸 찾으려고 줄 수 가중 평균을 왜 함께 봤는지 알게 됩니다.

**핵심 주장 (하나)**: 기준선의 약점은 "큰 파일이 읽기 어렵고 테스트하기 어렵다"는 한 가지로 모입니다. 단순 평균만으로는 이 약점이 흐려져서, 줄 수 가중 평균을 *함께* 봤습니다. 다만 줄 수 가중 평균도 한계가 있는 보조 지표입니다.
- 0편 마지막 약속("어떤 기준이 왜 약했는지, 줄 수 가중 평균을 왜 함께 보는지")을 이 편에서 지킵니다.
- 프레이밍 주의: 0편 게시본은 "줄 수에 가중치를 더 주었다"고 썼습니다. 이 편에서는 "단순 평균을 버린 게 아니라 **나란히 놓고 차이를 본다**"로 바로잡습니다. 두 숫자의 *차이*(5.46점)가 신호이고, 가중 평균 하나가 정답은 아닙니다.

### 뒷받침 facts 키
- 평균과 가중 평균의 차이: `file_mean`(84.23), `file_line_weighted_mean`(78.77), `gap_mean_minus_weighted`(5.46), `file_median`(85.06), `files_below_85`(1249)
- 큰 파일이 낮다: `lowest_files_score_range_examples`(7개 예시 전부 579~1,515줄, 60.44~67.16점), `files_over_400_lines`(69), `long_file_threshold_lines`(400), `low_score_types[2]`(800~1,500줄, analysability·testability 감점)
- 약한 기준: `criteria_mean_baseline.*`, `weakest_three.*`
- file_length 기준이 높은데도 큰 파일 문제가 있다는 역설: `criteria_mean_baseline.file_length`(4.916) vs `files_over_400_lines`(69) / `measured_files`(2515)
- 모델과 무관한 같은 방향의 신호(보조): `repo_rubric.functions_over_60_lines`(913), `repo_rubric.criteria.unit_size.score_before`(0)
- 측정 주의: `measurement_notes.judged_once_per_file`, `measurement_notes.judge_variance`

## 목차 (style-guide 구성 적용, 기준선 편이라 "개입"은 없음을 밝힘)

### 0. 한 줄 요약 (인용문)
- 위 한 줄 약속을 그대로 씁니다. packager가 publish.md에서 Velog 설명란과 같은 문장으로 한 번만 만듭니다.

### 1. 도입: 평균이 괜찮으면 아무도 안 고친다 (문제)
- 시작은 작성자 상황: 스타트업에서 AI로 기능을 빠르게 붙이다 보니 파일이 커지는데, "평균 84점"이라는 숫자를 보면 급하지 않다고 느끼게 된다는 것. 회고형("우리는 처음에 평균만 보고 안심했습니다")으로 씁니다.
- 0편 요약은 반복하지 않고 링크 한 줄로 대신합니다: "두 루브릭과 10개 기준은 [0편]에 정리했습니다."
- 수치: `file_mean` 84.23, `file_median` 85.06, `grade_a_files` 699(90점 이상), `files_below_85` 1249
- 쓸 내용: 중앙값(85.06)이 평균(84.23)보다 높다는 것은 낮은 점수 쪽 꼬리가 평균을 끌어내린다는 뜻으로 읽을 수 있다(해석이라고 밝힘). 측정 대상 2,515개 중 1,249개가 85점 미만.
- 판정 모델 고지(이 편 첫 등장 시 1회): Decision Model Clef가 파일당 한 번 판정했고, 점수는 실행마다 조금 달라질 수 있다.
- Verdict 저장소 링크를 이 섹션에 겁니다.

### 2. 어떤 기준이 왜 약했나 (가설 ①)
- 그래프: **기준별 평균 막대그래프 1개** (`criteria_mean_baseline` 10개, 0~5점 축, 낮은 순 정렬). <!-- viz:bar criteria_mean_baseline sort=asc -->
  - 10개 기준 이름을 글머리로 다시 나열하지 않습니다(0편 링크). 그래프가 그 역할을 합니다.
- 글머리 목록으로 약한 3개만:
  - comments 3.91
  - testability 4.14
  - analysability 4.19
- "왜"에 대해 facts가 받쳐 주는 범위:
  - testability·analysability: `low_score_types[2]`에서 800~1,500줄 서비스·repository·스키마가 이 두 기준에서 감점됐다고 기록돼 있습니다. API route(62~69점)와 클라이언트 훅(69.8점 등)도 여러 역할이 한 함수·한 파일에 섞인 유형입니다. 즉 "한 곳에 역할이 몰리면 읽기도, 떼어 테스트하기도 어렵다"로 묶을 수 있습니다. 세 유형 자체의 소개는 0편에 있으므로 점수 범위만 새로 덧붙입니다.
  - 모델과 무관한 보조 신호: repo 루브릭에서 60줄 넘는 함수가 913개, unit_size 점수 0. 판정 모델 점수와 독립적인 지표가 같은 방향을 가리킨다는 정도로만 씁니다(인과라고 쓰지 않음).
  - **comments: 왜 약했는지 facts에 근거가 없습니다. "미확인"으로 둡니다.** 사람 확인 질문 1번 참고. 근거가 오지 않으면 본문에서는 "가장 낮았지만 이유는 이번 라운드에서 따로 들여다보지 않았다"로 정직하게 씁니다.
- 역설 한 문단: file_length 기준 평균은 4.916으로 높은 편입니다. 400줄 넘는 파일은 2,515개 중 69개뿐이라 파일 단위로 평균을 내면 거의 드러나지 않습니다. 그런데 바로 그 소수의 큰 파일에 낮은 점수가 몰려 있었습니다. 이것이 다음 섹션으로 넘어가는 다리입니다. (비율 퍼센트는 facts에 없으므로 "69개/2,515개"로만 표기)

### 3. 줄 수 가중 평균을 왜 함께 보나 (가설 ②)
- 표: **평균 지표 비교 표**
  | 지표 | 값 |
  |---|---:|
  | 파일 루브릭 평균 | 84.23 (`file_mean`) |
  | 중앙값 | 85.06 (`file_median`) |
  | 줄 수 가중 평균 | 78.77 (`file_line_weighted_mean`) |
  | 차이(평균 − 가중) | 5.46 (`gap_mean_minus_weighted`) |
- 표: **점수가 낮은 파일 예시** (`lowest_files_score_range_examples`, 역할·점수·줄 수 3열). 제목은 "낮은 점수 파일 예시"로 하고 "최저 N개"라고 쓰지 않습니다(전체 순위가 아니라 예시임).
  - 워커 런타임 모듈 60.65 / 786줄, 평가 repository 60.44 / 1,515줄, 결과 클라이언트 모듈 67.16 / 579줄, 링크 repository 63.17 / 1,269줄, 지원자 제출 repository 62.97 / 877줄, 집계 캐시 서비스 65.65 / 770줄, 최종 검토 서비스 67.16 / 845줄
  - "지원자 제출 repository", "평가 repository"는 redaction rename 목록에 없는 라벨이라 redactor 확인 대상으로 표시합니다.
- 논지: 단순 평균은 10줄짜리 파일과 1,500줄짜리 파일을 같은 1표로 셉니다. 사람이 읽고 고치는 시간은 줄 수에 더 가깝기 때문에, "읽는 코드 기준으로 보면 몇 점인가"를 보려고 가중 평균을 옆에 둡니다. 두 값이 5.46점 벌어졌다는 것이 "큰 파일일수록 점수가 낮은 경향"의 신호였습니다.
- 정직성 단락 (반드시 포함):
  - 가중 평균은 *좋은 지표라서* 고른 게 아니라 *단순 평균이 가리는 것을 보려고* 옆에 둔 보조 지표입니다.
  - 한계 1: 낮은 점수의 큰 파일을 작은 파일 여럿으로 쪼개기만 해도 가중 평균은 오릅니다. 품질이 그대로여도 숫자는 움직입니다. 기준선 시점에는 아직 분할 전이라 이 문제가 없지만, 이후 편에서 이 지표를 개선 근거로 쓸 때는 반드시 다른 지표와 함께 봐야 합니다(0편에서 이미 짚은 내용은 링크로).
  - 한계 2: 줄 수는 "얼마나 읽기 어려운가"의 대리값일 뿐입니다. 줄이 길어도 단순한 파일, 짧아도 핵심인 파일의 차이는 반영하지 못합니다.
  - 한계 3: 차이 5.46점은 집계 수준의 경향입니다. 파일 점수와 줄 수의 상관을 직접 계산한 값은 facts에 없으므로 "상관이 있다"고 수치로 단정하지 않습니다.

### 4. 기준선에서 정한 것 (측정 결과 대신)
- 기준선 편이라 전→후 표는 없습니다. 이 사실을 한 문장으로 밝힙니다.
- 대신 이 관찰이 무엇으로 이어졌는지 1~2문장: 큰 파일과 역할이 섞인 파일을 먼저 다룬다는 우선순위. 구체적 작업과 결과는 02편 이후로 넘깁니다(첫 주 결과 수치는 0편 링크로 대체, 여기서 반복하지 않음).
- 앱별 평균(`workspace_mean_baseline`: 평가 앱 83.41, 웹 앱 84.72, 인증 앱 82.36)은 넣지 않는 것을 기본으로 합니다. 핵심 주장과 거리가 있고 차이도 작습니다. writer가 분량이 모자랄 때만 한 줄로 씁니다.

### 5. 남은 문제
- comments가 가장 약한 이유는 미확인입니다(데이터 요청 중이면 그렇게 씁니다).
- 등급은 A(90점 이상, 699개)와 D(70점 미만, 108개)만 알고, B·C 경계와 파일 수, 점수 분포는 이번 글에 싣지 못했습니다. → facts의 `unknown` 항목. 글에서는 "분포는 미확인"이라고만 적고 추정치를 쓰지 않습니다.
- 줄 수 가중 평균의 분할 효과는 이후 편에서 따로 분리해 볼 방법이 아직 없습니다(06편 측정 편과 연결).
- 판정은 파일당 1회라, 기준별 평균의 소수점 차이(예: testability 4.14와 analysability 4.19의 0.05 차)는 판정 분산 안에 있을 수 있습니다. 순위를 과하게 해석하지 않습니다.

## 반드시 밝힐 한계와 실패
- 판정 모델(Decision Model Clef) 점수는 실행마다 조금 달라질 수 있고 파일당 1회만 판정했습니다.
- 줄 수 가중 평균은 파일 분할만으로 오를 수 있는 지표입니다. "좋은 지표"라고 단정하지 않고 보조 지표로 위치시킵니다.
- comments가 약한 이유는 미확인입니다.
- 점수 분포, B·C 등급 경계, 기준별 최저 파일은 데이터가 없어 다루지 않습니다.
- 실패/반성 한 줄(회고형): 처음엔 단순 평균만 보고 "괜찮다"고 판단할 뻔했다는 점. 사실 확인 필요(질문 2번 참고).

## 직전 편(00-intro)과 겹치는 내용 → 링크로 대체
- 두 루브릭 소개 표 → "[0편]의 '점수는 두 가지로 나눴습니다'"
- 10개 기준 나열 → 0편 링크 + 이 편은 그래프로만 보여 줌
- 기준선 요약 글머리(2,515개, 84.23, D등급 108개, 78.77, 약한 3기준, repo 44.1) → 이 편에서 *해석*만 추가하고 요약 목록은 반복하지 않음
- 낮은 점수 유형 3개 설명 → 0편 링크, 이 편은 점수 범위(62~69점, 69.8점 등, 800~1,500줄)만 덧붙임
- 첫 주 결과 표와 "가중 평균이 더 올랐다"는 해석 → 0편 링크. 분할 효과 한계는 이 편에서 *기준선 관점*으로만 다시 짚음

## 사람이 확인할 질문 (확인 전 writer 실행 금지)
1. **comments가 가장 약했던 이유**: facts에 근거가 없습니다. 판정 근거 샘플(낮은 comments 점수를 받은 파일 몇 개의 역할과 판정 사유 요약)을 줄 수 있나요? 없으면 본문에 "미확인"으로 두겠습니다. 같은 맥락에서 기준별 최저 파일 목록과 점수 분포(히스토그램, B·C 경계)도 있으면 받고 싶습니다. 없으면 이번 편에서는 빼겠습니다.
2. **작성자 맥락 확인**: 도입에 "처음엔 평균 84점만 보고 급하지 않다고 느꼈다"는 회고를 쓰려고 합니다. 실제로 그랬나요? 줄 수 가중 평균을 처음 보게 된 계기(누가 제안했는지, AI로 짠 큰 파일이 눈에 띄어서였는지 등)가 따로 있다면 알려 주세요. 0편의 "가중치를 더 주었다"는 표현을 "함께 본다"로 바로잡는 것도 괜찮은지 확인 부탁드립니다.
3. **스코어보드 처리**: 기준선 편이라 "이번 편 시점" 열을 기준선과 같은 값, 변화를 "—"로 두고 현재 값은 0편 링크로 넘기려 합니다. 아니면 2026-11-14 현재 값을 다시 넣을까요? (현재 값을 넣으려면 해당 수치를 facts.json에 추가해야 합니다.)

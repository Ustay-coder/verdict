# Verdict 관리 평면(M1a) 상세 설계 (v1.0)

- 상태: **구현을 마쳤고(2026-11-10) `@verdict-ai/*` 0.2.0으로 배포했다(2026-11-11).** 항목 1–8의 결정(C1–C24)을 구현했다(§10). 그 뒤 "어느 컴퓨터에서든 서버의 버전을 이름으로 받아 쓴다"를 정해 구현했다(C25–C28, §11, 2026-11-11. 다음 배포에 들어간다). 이 문서는 그 결정의 기록이다. 쓰는 방법은 README와 문서 사이트에 있다.
- 입력: 수익 모델 문서(R1–R15)와 [hub.md](hub.md)(Verdict Hub 설계). 수익 모델 문서(`revenue.md`)와 호스팅 서비스의 팀 기능 문서(`team.md`)는 이 저장소에 없다. 아래에서 `revenue.md §…`, `R…`, `team.md T…`로 가리키는 것은 그 문서들의 항목이고, 이 문서를 읽는 데 필요한 내용은 여기에 적었다.
- 범위: revenue.md §8의 **M1a**. 공개 저장소(MIT)에 두는 것만 다룬다: rubric 버전을 서버에 올리고 내려받는 API, 프로젝트, 환경 포인터, 실행 요약 보고 API, CLI, SDK의 환경 읽기. 조직·멤버·역할·한도·결제는 M1b 이후이고 비공개 저장소에 둔다(R8).
- 표기: **[결정]** 채택한 기준. 이 문서의 결정은 `C1`부터 번호를 붙인다.

## 2. 결정 기록

| # | 결정 | 고려한 다른 선택지와 비용 |
| --- | --- | --- |
| **C1** | **버전은 프로젝트에 속한다.** 같은 버전을 두 프로젝트에서 쓰면 프로젝트마다 한 번씩 저장한다 | 계정 전체에 한 번만 보관하면 중복이 없지만, 한 프로젝트만 볼 수 있는 사람이 다른 프로젝트의 rubric도 읽게 된다. Enterprise의 프로젝트별 권한(R13)을 넣을 때 이미 공유된 버전의 처리가 남는다. rubric 문서는 작아서 중복 저장 비용은 거의 없다 |
| **C2** | 서비스가 rubric을 부르는 이름은 **올릴 때 정하는 짧은 이름**이다. 기본값은 rubric 문서의 `id`, 없으면 파일 이름(`rubrics/intent.yaml` → `intent`). `--name`으로 바꿀 수 있다 | rubric 문서의 `name`을 그대로 쓰면 따로 정할 것이 없지만, `name`은 화면에 보이는 제목이라 주소에 쓰기 어렵고 제목을 고치면 서비스가 읽던 포인터와 끊긴다 |
| **C3** | **프로젝트와 환경은 직접 만든다.** 없는 프로젝트나 환경에 올리거나 승격하면 거절한다. 만드는 일은 서버 API가 하고 CLI는 그 API를 부르기만 한다. 나중에 웹 화면이 같은 API로 만들 수 있게 하기 위해서다(§3.3) | 처음 쓸 때 자동으로 만들면 단계가 하나 줄지만, CI 설정의 오타로 새 프로젝트가 조용히 생긴다. 무료 한도(R9)가 막는 것이 "두 번째 환경 생성"이라 생성이 별도 동작이어야 한도를 걸 자리가 분명하다 |
| **C4** | 포인터는 **환경 안에서 rubric 이름마다 하나**다. `prod`의 `intent`와 `urgency`가 각각 버전을 가리킨다. 여러 rubric을 함께 바꿀 때는 한 요청에 담아 동시에 적용한다 | 환경이 rubric 버전 목록 한 장을 통째로 가리키면 조합이 항상 맞고 한 번에 전체를 되돌릴 수 있지만, rubric 하나만 바꿔도 목록 전체를 새로 만들어야 하고 이력에서 무엇이 바뀌었는지 두 목록을 비교해야 알 수 있다. 감수하는 것: 함께 바꾼 rubric들을 함께 되돌리려면 사람이 둘을 같이 지정해야 한다 |
| **C5** | 버전은 **내 컴퓨터나 CI에서 고정한 것을 그대로 올린다.** 서버는 받은 문서로 id를 다시 계산해 보낸 id와 다르면 거절한다. 원본은 저장소의 rubric 파일 하나다 (**이 마지막 문장은 C25로 바뀌었다**: 원본은 서버의 버전이다) | 서버에 있는 수정 가능한 rubric(`/v1/rubrics`)을 서버가 고정하는 방식(hub.md §10.1 초안)은 원본이 저장소 파일과 서버 두 곳이 되어, 둘이 어긋났을 때 어느 쪽이 맞는지 정해야 한다. 첫 구매자는 rubric을 저장소에 두는 개발팀이다(R1) |
| **C6** | 버전은 **필요할 때 자동으로 올린다.** 승격하거나 실행 요약을 보고할 때 그 버전이 서버에 없으면 함께 올린다. 따로 올리는 명령(`verdict push`)도 둔다 | 반드시 먼저 올리게 하면 무엇이 서버로 가는지 분명하지만 매번 명령이 두 개가 된다. 버전은 내용이 같으면 id가 같아 여러 번 올려도 결과가 같다. CI 키가 보고하면서 버전을 올려도 되는지는 항목 5에서 정한다 |
| **C7** | **어떤 환경도 가리키지 않는 버전만 지울 수 있다.** 승격 이력과 실행 요약에는 버전 id가 남고 "삭제된 버전"으로 보인다. 같은 파일을 다시 올리면 같은 id로 복구된다 | 지울 수 없게 하면 이력이 항상 온전하지만 실수로 올린 문서를 없애려면 프로젝트를 통째로 지워야 한다. 언제든 지울 수 있게 하면 운영 중인 포인터가 없는 버전을 가리켜 서비스가 멈출 수 있다 |
| **C8** | 승격 요청은 **"지금 가리키는 버전"을 함께 보내고, 서버의 현재 상태와 다르면 거절한다.** 사람이 현재 상태를 다시 보고 결정한다 | 나중에 보낸 것이 이기게 하면 항상 성공하지만, 거의 동시에 승격한 두 사람 중 뒤 사람이 앞 사람의 승격을 모르고 덮어쓴다 |
| **C9** | **되돌리기 명령을 따로 둔다**(`verdict rollback`). 서버가 이력에서 직전 버전을 찾아 포인터를 바꾸고 이력에 "되돌림"으로 남긴다 | 이전 버전을 다시 승격하는 것만 두면 만들 것이 없지만, 장애 중에 버전 id를 찾아야 하고 이력에서 승격과 되돌림이 구분되지 않는다 |
| **C10** | 승격의 **사유 메모는 선택**이다. 쓰면 이력에 남는다 | 필수로 하면 이력이 항상 설명을 갖지만 급할 때 의미 없는 메모가 쌓인다. 메모를 강제하는 규칙은 Pro의 승격 승인(M2a)에서 조직별 설정으로 넣을 수 있다 |
| **C11** | 서비스의 SDK는 **받아 둔 버전을 쓰고 일정 주기로 다시 확인한다.** 기본 60초, 서비스가 바꿀 수 있다 | 판정할 때마다 서버에 물으면 항상 최신이지만 판정마다 지연이 붙고 서버가 느려지면 서비스도 느려진다. 시작할 때 한 번만 읽으면 승격을 반영하려고 서비스를 재시작해야 한다. 감수하는 것: 승격과 되돌리기가 반영되기까지 최대 60초가 걸린다 |
| **C12** | 실행 중에 서버가 응답하지 않으면 **마지막으로 받은 버전을 계속 쓴다.** 확인 실패는 서비스가 알 수 있게 알린다 | 오류를 내면 오래된 버전으로 판정하는 일은 없지만 Verdict 서버의 장애가 고객 서비스의 장애가 된다(revenue.md §3.4와 같은 방향) |
| **C13** | 시작할 때 서버가 응답하지 않으면 **오류를 낸다. 서비스가 예비 rubric을 지정했으면 그것을 쓴다.** 예비 rubric은 서비스와 함께 배포한 저장소의 rubric 파일이고, 지정은 선택이다 | 무조건 오류를 내면 Verdict 서버가 죽어 있는 동안 서비스를 새로 배포하거나 재시작할 수 없다. 마지막 버전을 디스크에 저장해 두는 방식은 컨테이너나 Workers처럼 디스크가 재시작마다 비는 환경에서 동작하지 않는다 |
| **C14** | **CI 키도 보고에 딸린 버전은 올릴 수 있다.** 승격, 되돌리기, 버전 삭제는 사람만 한다. revenue.md §5의 역할 표를 이에 맞게 고쳤다 | 버전 없이 숫자만 받으면 사람이 그 버전을 올리기 전까지 "이 숫자가 어떤 rubric의 것인지" 내용을 볼 수 없다. 사람이 먼저 올려야 보고할 수 있게 하면 PR마다 작성자가 직접 올려야 해서 CI 흐름이 끊긴다. 감수하는 것: 좌석 1개만 사고 버전은 전부 CI로 올리는 팀이 생길 수 있다. 운영에 무엇을 쓸지 정하는 일은 여전히 사람 좌석이 한다(R5) |
| **C15** | 실행 요약에 **출처(커밋, 브랜치, CI 실행 링크), 데이터셋 파일 이름, 사용량(모델 호출 수, 토큰 수)을 함께 보낸다.** 출처는 GitHub Actions에서 자동으로 채우고 옵션으로 끌 수 있다 | 숫자만 보내면 서버에 남는 것이 가장 적지만 요약을 커밋과 연결하거나 데이터셋별로 시간순으로 묶을 수 없다. 묶지 못하면 지표 하락 알림(M2b)을 만들 수 없다. 감수하는 것: 브랜치 이름과 파일 이름이 서버에 남는다 |
| **C16** | **비교 요약 보고를 M1a에서 함께 만든다**(`verdict diff --report`). 분류별 건수, 조건 차이, 양쪽 실행과 버전 id를 보낸다. 어떤 사례인지는 보내지 않는다 | 승격 승인을 만드는 M2a로 미루면 M1a가 작아지지만, 무료로 공개한 뒤(M1b) 쌓이는 보고에 비교 건수가 없다. 수정·회귀 건수는 실행 요약 두 개로 계산할 수 없다. 일치 수가 같아도 3건이 좋아지고 3건이 나빠졌을 수 있다 |
| **C17** | 승격·보고 명령은 **허브의 주소와 로그인을 그대로 쓴다.** `verdict login`을 `verdict hub login`과 같은 뜻의 명령으로 추가한다. 로그인 파일은 **서버 주소별로 키를 보관**하도록 바꾼다 | 새 설정(`VERDICT_CLOUD_URL` 등)을 만들면 이름은 분명하지만 같은 서버에 설정과 로그인이 두 벌이 된다(R7과 어긋남). `VERDICT_API_URL`을 쓰면 그 값이 켜진 동안 `run`·`diff`가 막혀 "실행하고 보고"를 한 번에 할 수 없다. 주소별 보관은 자체 호스팅 팀이 승격은 팀 서버에, 발행은 공개 허브에 하기 위해 필요하다 |
| **C18** | 프로젝트는 **저장소에 커밋하는 `verdict.yaml`에 적는다.** `--project`와 `VERDICT_PROJECT`로 덮어쓸 수 있다. 서버 주소도 같은 파일에 적을 수 있다. 키는 적지 않는다 | 옵션과 환경 변수로만 받으면 새 파일이 없지만 사람이 승격할 때마다 프로젝트를 적거나 각자 환경 변수를 맞춰야 하고, 잘못된 프로젝트에 승격할 여지가 생긴다 |
| **C19** | `verdict promote <파일>`은 **파일이 `verdict.lock`에 적힌 버전과 같을 때만 승격한다.** 그 버전의 실행 요약이 서버에 없으면 경고만 한다 | 검사하지 않으면 시험하지 않은 수정이 섞인 채로 운영에 올라갈 수 있다. 실행 요약이 없을 때 거절까지 하는 것은 Pro의 승격 승인이 서버에서 할 일이고(R13), CLI의 검사는 다른 도구로 우회할 수 있어 규칙으로서 의미가 약하다 |
| **C20** | 공개 코드에 **"이 요청을 허용할까?"를 묻는 자리를 하나 둔다.** 관리 경로는 일을 하기 전에 누가, 무엇을, 어디에 하려는지를 그 자리에 넘긴다. 공개 저장소의 기본 답은 항상 허용이고, 클라우드는 이 자리에 역할·한도·승인 검사를 꽂는다(§9.1) | 비공개 코드가 주소를 보고 앞에서 막으면 공개 코드는 바뀌지 않지만, 비공개 코드가 공개 경로의 주소와 요청 형식을 따로 알아야 한다. 공개 저장소에 새 경로를 추가하고 비공개 쪽에서 막는 것을 빠뜨리면 그 경로는 클라우드에서 열린 채로 나간다 |
| **C21** | **클라우드 빌드에서는 평가 실행 경로를 끈다.** 앱을 만들 때 경로 묶음을 고를 수 있게 한다. 자체 호스팅은 전부 켜고, 클라우드는 허브와 관리 경로만 켠다(§9.2) | 그대로 두면 만들 것이 없지만, 요청에 담긴 사례가 클라우드에 도착해 평가 기록으로 저장된다. "클라우드는 숫자만 받는다"(R2)와 어긋난다 |
| **C22** | 웹 화면은 **M1b에서 만든다.** 클라우드를 무료로 공개할 때 함께 나온다 | M1a에 넣으면 자체 호스팅에서도 바로 화면을 쓰지만, M1a에는 로그인과 사람이 없어 화면에 API 키를 붙여 넣는 방식이 되고 뒤의 단계가 전부 밀린다. M2a 이후로 미루면 M1b가 작아지지만 무료 공개 때 CLI만 있다. M1b에는 Google 로그인, 멤버 초대, 역할 지정 때문에 브라우저가 어차피 필요하다 |
| **C23** | 웹 화면에서 **조작까지 한다**: 프로젝트와 환경 만들기, 포인터 보기, 승격, 되돌리기, 이력과 실행 요약 보기, 멤버 초대. 버전 올리기는 CLI와 CI만 한다 | 보기와 조직 관리만 두면 화면이 작아지지만, 장애 중에 급하게 하는 되돌리기를 CLI로만 해야 한다. 서버 API가 그 일을 이미 다 하므로(C3, C8, C9) 화면은 부르기만 한다 |
| **C24** | 웹 화면 코드는 **비공개 저장소에 둔다.** 클라우드에서만 제공하고, 자체 호스팅은 CLI와 API로 쓴다. 자체 호스팅 사용자의 요청이 쌓이면 공개를 다시 본다 | 공개 저장소에 두면 자체 호스팅도 화면을 쓰지만, 로그인이 없는 공개판 화면과 로그인이 있는 클라우드 화면을 함께 유지해야 한다. MIT로 공개한 것은 되돌릴 수 없어(revenue.md §7) 비공개로 시작해 나중에 여는 것만 가능하다 |

## 3. 구조

```
계정(API 키가 속한 테넌트)
└─ 프로젝트 support-bot
   ├─ rubric intent                         (C2)
   │   └─ 버전: rv_a1…, rv_b2…, rv_c3…    (C1)
   ├─ rubric urgency
   │   └─ 버전: rv_d4…
   ├─ 환경 prod
   │   ├─ intent  → rv_b2…                  (C4)
   │   └─ urgency → rv_d4…
   ├─ 승격 이력
   └─ 실행 요약
```

### 3.1 용어

- **프로젝트**: 서비스 하나에 대응하는 묶음. 버전, 환경, 승격 이력, 실행 요약이 프로젝트에 속한다. 프로젝트 사이에는 아무것도 공유하지 않는다(C1).
- **환경**: `prod`, `staging` 같은 이름. 프로젝트 안에서 만든다.
- **포인터**: 환경 안에서 rubric 이름이 가리키는 버전(`rv_…`). 승격은 포인터를 바꾸는 일이다.
- **버전**: 내용이 바뀌지 않는 rubric 문서. id는 내용에서 계산하므로(`core/src/versions/rubric-version.ts`) 같은 내용은 어느 컴퓨터에서 고정해도 같은 id다.

### 3.2 이름 규칙

- 프로젝트 이름, 환경 이름, rubric 이름(C2)은 모두 같은 규칙을 쓴다: 소문자·숫자·`-`, 63자 이하. 공개 허브의 slug 규칙(`core/src/hub/publication.ts`)과 같다.
- rubric 문서의 `id`나 파일 이름이 이 규칙에 맞지 않으면 CLI는 이름을 자동으로 고치지 않고, `--name`을 요구한다.
- rubric 이름은 프로젝트 안에서 하나다. `prod`의 `intent`와 `staging`의 `intent`는 같은 rubric의 서로 다른 버전을 가리킨다.

### 3.3 웹 화면을 위해 미리 지키는 것 (C3)

M1a는 API와 CLI만 만든다. 웹 화면은 M1b에서 비공개 저장소에 만든다(C22, C24). 그때 API를 바꾸지 않도록 지금 다음을 지킨다.

- 만들기·바꾸기는 전부 REST API 요청 하나로 끝난다. CLI만 아는 규칙을 두지 않는다. 이름 검사, 중복 검사는 서버가 한다.
- 거절할 때는 이유를 구분할 수 있는 값으로 돌려준다(이름이 규칙에 맞지 않음, 이미 있음, 한도 초과). 화면이 그 값을 보고 안내문을 고를 수 있어야 한다.
- 요청한 사람을 확인하는 자리를 API 키에 묶지 않는다. 웹 로그인(M1b)으로 들어온 사람도 같은 경로를 쓴다(§9.1).

웹 화면이 다루는 것(C23)은 이미 올라온 버전을 어느 환경에 쓸지다. rubric의 원본은 저장소 파일이므로(C5) 웹에서 rubric 내용을 고치지 않는다. 그것은 호스팅 워크벤치(revenue.md §8 후속)에 속한다. 화면에서 하는 승격은 `rv_…`를 지정한 승격과 같아서 lock 파일 검사(C19)는 없고, 실행 요약이 없다는 경고만 보여준다.

### 3.4 현재 코드와의 차이

| 필요한 것 | 현재 | 할 일 |
| --- | --- | --- |
| 프로젝트, 환경, 포인터 | 없음 | 새로 만든다 |
| 서버의 버전 보관 | `VersionStore`(`core/src/versions/store.ts`)를 메모리·파일 저장소만 구현. DB 저장소(`db/src/store.ts`)에는 없다 | DB 저장소에 추가한다. `VersionStore`는 사례를 담은 데이터셋과 사례 id를 담은 실행 기록도 다루므로 통째로 구현하지 않고, 버전 부분만 나눠서 쓴다(R2) |
| 계정마다 같은 버전 id | 버전 id는 내용에서 나오므로 두 계정·두 프로젝트가 같은 id를 가질 수 있다 | 버전의 키는 id 하나가 아니라 계정 + 프로젝트 + id다 |

## 4. 버전 올리기·내려받기 (C5–C7)

### 4.1 규칙

- **버전은 rubric 이름 아래에 올린다.** `intent`로 올린 버전은 `intent` 포인터만 가리킬 수 있다. `urgency` 포인터를 `intent` 버전으로 바꾸는 요청은 서버가 거절한다. 같은 내용을 두 이름으로 올리면 이름마다 따로 저장한다.
- **rubric 이름은 처음 올릴 때 생긴다.** 프로젝트·환경과 달리 미리 만들지 않는다. rubric 개수에는 과금하지 않으므로(revenue.md §1) 한도를 걸 자리가 필요 없다.
- **무결성(C5)**: 서버는 받은 rubric을 다시 고정해 id가 요청과 같은지 확인한다. 공개 발행의 검사(`buildPublication`)와 같다. 이미 있는 버전을 다시 올리면 저장된 것을 그대로 돌려준다.
- **받는 범위**: 유효한 rubric은 모두 받는다. 공개 발행의 제한(기준 1개, `baseUrl` 금지, 라이선스 필수)은 적용하지 않는다. 팀 안에서만 보는 문서이기 때문이다. 요청 크기는 1 MB 이하.
- **부모**: 부모 버전이 서버에 없어도 받는다. 부모 id, 바뀐 종류(`changeKinds`), 메모는 기록한다.
- **내려받기**: 클라이언트는 받은 문서를 다시 고정해 서버가 말한 id와 같을 때만 쓴다. `verdict pull hub:…`의 검사와 같다. CLI가 이름으로 받아 쓰는 방법과 파일로 내려받는 방법은 §11(C25–C28)에 있다.
- **지우기(C7)**: 어느 환경의 포인터든 그 버전을 가리키면 거절한다. 포인터를 다른 버전으로 옮기거나 내린 뒤에 지울 수 있다.
- 기존의 수정 가능한 rubric(`/v1/rubrics`)은 그대로 둔다. 버전 API와 서로 참조하지 않는다.

### 4.2 REST (PR 2에서 확정)

| Method | Path | 목적 |
| --- | --- | --- |
| `POST` | `/v1/projects/:project/rubrics/:name/versions` | 버전 올리기. 본문 `{ id, rubric, parentVersionId?, fork? }`. 새로 저장하면 201, 이미 있으면 200. 응답 `{ version, created }`. id가 내용과 다르면 400, 1 MB를 넘으면 413 |
| `GET` | `/v1/projects/:project/rubrics` | rubric 이름 목록. 이름마다 버전 수와 마지막으로 올린 시각 |
| `GET` | `/v1/projects/:project/rubrics/:name/versions` | 버전 목록, 최신순. rubric 문서는 빼고 준다 |
| `GET` | `/v1/projects/:project/rubrics/:name/versions/:id` | 버전 하나(rubric 문서, 해시, 부모 정보) |
| `DELETE` | `/v1/projects/:project/rubrics/:name/versions/:id` | 지우기. 포인터가 가리키면 409(`in_use`) |

README REST 표, SDK(`versions`), OpenAPI에 같은 내용을 넣었다(AGENTS.md).

## 5. 승격과 이력 (C8–C10)

### 5.1 규칙

- **승격할 수 있는 버전**: 그 rubric 이름 아래 올라와 있는 버전이면 된다(§4.1). 승인, "회귀 0건" 같은 조건은 Pro 기능이라 공개 코드에 넣지 않는다(R8, R13). 환경 사이의 순서(`staging`을 거쳐야 `prod`)도 강제하지 않는다.
- **현재 상태 확인(C8)**: 요청의 변경마다 `expected`(지금 가리키는 버전, 포인터가 없으면 `null`)가 필수다. 하나라도 다르면 요청 전체를 거절하고 현재 상태를 돌려준다.
- **여러 rubric(C4)**: 한 요청에 담은 변경은 전부 적용되거나 전부 거절된다. 한 요청은 환경 하나의 변경만 담고, rubric 하나는 한 번만, 최대 20개까지 담는다(§9.3).
- **처음 승격**: 환경에 그 이름의 포인터가 없으면 새로 생긴다.
- **환경 사이 승격**: `--from staging`은 `staging`이 가리키는 버전을 읽어 대상 환경에 승격한다. 서버에서는 보통의 승격이다.
- **승격 전 확인**: CLI가 "`prod`의 `intent`: `rv_b2…` → `rv_c3…`"을 보여주고 확인을 묻는다. 터미널이 없으면 `--yes`가 필요하다. `verdict publish`와 같다.
- **되돌리기(C9)**: 포인터의 가장 최근 변경을 되돌린다. 변경이 한 번뿐이면(처음 승격) 되돌릴 버전이 없으므로 거절한다. 되돌린 직후 다시 되돌리면 되돌리기 전 버전으로 돌아간다. C8의 확인을 똑같이 한다.
- **포인터 내리기**: 환경에서 rubric 하나의 포인터를 없앤다. 이력에 남는다. C7에 따라 버전을 지우려면 먼저 내리거나 다른 버전으로 옮긴다.
- **환경·프로젝트 삭제**: 요청에 이름을 다시 적어야 지워진다. 환경을 지워도 그 환경의 이력은 프로젝트에 남는다. 프로젝트를 지우면 버전, 환경, 이력, 실행 요약이 전부 지워진다.

### 5.2 이력

- 한 줄에 남는 것: 시각, 환경, rubric 이름, 이전 버전, 새 버전, 종류(승격·되돌림·내림), 메모(C10), 누가 했는지.
- **"누가"**: M1a에서는 API 키의 이름이다. 사람 이름이 남는 것은 조직과 로그인이 생기는 M1b부터다(R8).
- 이력을 고치거나 지우는 API는 없다.
- 오래된 이력을 지울 때에도 **포인터마다 가장 최근 변경 한 건은 남긴다**(team.md T25). 되돌리기가 그 줄을 읽기 때문이다.
- 공개 코드에는 보관 기간이 없다. 오래된 이력을 지우는 것은 클라우드의 플랜 규칙이 한다(R9, R13). 그 규칙이 쓸 "이 날짜 이전 삭제" 동작은 공개 저장소의 저장소 계층에 둔다.

### 5.3 REST (PR 2에서 확정)

| Method | Path | 목적 |
| --- | --- | --- |
| `POST` · `GET` | `/v1/projects` | 프로젝트 만들기(`{ name }`) · 목록. 이미 있으면 409(`already_exists`) |
| `DELETE` | `/v1/projects/:project` | 프로젝트 삭제. 본문 `{ confirm: "<이름>" }` |
| `POST` · `GET` | `/v1/projects/:project/environments` | 환경 만들기 · 목록 |
| `GET` | `/v1/projects/:project/environments/:env` | 환경과 포인터 전체: `{ name, createdAt, pointers: [{ name, versionId, updatedAt }] }` |
| `DELETE` | `/v1/projects/:project/environments/:env` | 환경 삭제. 본문 `{ confirm: "<이름>" }` |
| `POST` | `/v1/projects/:project/environments/:env/promotions` | 승격·내리기. 본문 `{ changes: [{ name, versionId, expected }], note? }`. `versionId: null`이면 내리기. 응답 `{ events }` |
| `POST` | `/v1/projects/:project/environments/:env/rollbacks` | 되돌리기. 본문 `{ name, expected, note? }`. 응답 `{ event }` |
| `GET` | `/v1/projects/:project/history?environment=&name=&limit=` | 이력, 최신순 |

### 5.4 거절할 때의 답 (PR 2에서 확정)

거절은 모두 `{ error: { type, message, … } }` 형식이다. 화면과 CLI는 `type`으로 안내문을 고른다(§3.3).

| 상황 | HTTP | `type` | 덧붙는 값 |
| --- | --- | --- | --- |
| `expected`가 현재 상태와 다름(C8) | 409 | `pointer_conflict` | `current`: 요청에 담긴 rubric마다 지금 가리키는 버전(`null`이면 포인터 없음) |
| 그 이름 아래 없는 버전으로 승격 | 400 | `unknown_version` | |
| 되돌릴 이전 버전이 없음 | 409 | `nothing_to_roll_back` | |
| 포인터가 가리키는 버전을 지움(C7) | 409 | `in_use` | |
| 이미 있는 프로젝트·환경을 만듦 | 409 | `already_exists` | |
| 없는 프로젝트·환경·버전 | 404 | `not_found` | |
| 허용 여부를 묻는 자리에서 거절(§9.1) | 403 | `forbidden` · `limit_exceeded` · `approval_required` | 거절한 쪽이 덧붙인 값(예: 어느 한도인지 `limit`, `max`, `used`). 이 저장소만으로 띄운 서버는 덧붙이지 않는다 |

구현하면서 정한 세부 규칙(논의하지 않은 것):

- **아무것도 바꾸지 않는 승격은 거절한다(400).** 이미 가리키는 버전으로 다시 승격하거나, 없는 포인터를 내리는 요청이다. 이력에 의미 없는 줄이 쌓이고 되돌리기의 "가장 최근 변경"이 흐려지는 것을 막는다. CLI는 보내기 전에 걸러낸다.
- **내린 포인터도 되돌릴 수 있다.** 가장 최근 변경이 "내림"이면 되돌리기는 내리기 전 버전을 다시 가리키게 한다.
- **포인터가 없던 상태에서의 승격은 되돌릴 수 없다.** 처음 승격과 같다. 포인터를 없애려면 내리기를 쓴다.
- **되돌아갈 버전이 지워졌으면 거절한다**(`nothing_to_roll_back`). C7에 따라 포인터가 가리키지 않는 이전 버전은 지울 수 있기 때문이다.
- **지웠다가 같은 이름으로 다시 만든 환경**은 예전 환경의 이력으로 되돌리지 않는다. 이력은 프로젝트에 남아 조회되지만, 환경을 만든 시각 이전의 변경은 되돌리기 대상이 아니다.
- **허용 여부는 변경마다 묻는다.** 한 요청에 rubric이 여러 개면 rubric마다 한 번씩 묻고, 하나라도 거절되면 아무것도 적용하지 않는다.

## 6. 서비스가 읽는 방법 (C11–C13)

서비스는 SDK로 환경의 포인터를 받아 자기 쪽에서 자기 모델 키로 실행한다(R2). 판정 내용은 서버로 보내지 않는다.

### 6.1 규칙

- **환경 전체를 한 번에 읽는다.** SDK는 환경의 포인터 전부와 그 rubric 문서를 한 요청으로 받는다. rubric 두 개를 함께 승격했을 때(C4) 서비스가 하나만 새 버전인 상태를 보지 않는다.
- **다시 확인(C11)**: 주기가 지난 뒤의 첫 호출이 서버에 다시 묻는다. 타이머를 쓰지 않으므로 Workers에서도 동작한다. 바뀐 것이 없으면 서버는 본문 없이 "그대로"(304)라고 답한다. 응답이 짧은 제한 시간(기본 2초) 안에 오지 않으면 받아 둔 버전으로 진행한다.
- **받은 문서 확인**: SDK는 받은 rubric을 다시 고정해 서버가 말한 id와 같을 때만 쓴다(§4.1). 다르면 서버가 응답하지 않은 것으로 처리한다(C12, C13).
- **어디서 온 버전인지 알린다.** SDK가 돌려주는 값에는 rubric, 버전 id, 출처(서버에서 방금 확인함 · 확인에 실패해 받아 둔 것 · 예비)가 들어 있다. 서비스는 버전 id를 자기 로그에 남겨 "이 판정은 어느 버전으로 했는가"를 추적한다.
- **예비 rubric(C13)**: 서버에서 한 번이라도 받으면 그 뒤로는 받은 버전을 쓴다. 예비로 돌고 있는 동안에도 주기마다 서버를 다시 확인한다.
- **특정 버전 읽기**: 포인터 대신 `rv_…`를 지정해 받는 길을 둔다(§4.2). 테스트와 재현에 쓴다.
- **서버는 읽기를 기록하지 않는다.** 읽을 때마다 DB에 쓰면 비용이 커진다. "이 환경을 서비스가 읽고 있는가"를 보여주는 기능은 필요해질 때 다시 본다.
- **승격을 서비스에 즉시 밀어 주는 방식(webhook 등)은 만들지 않는다.** 60초 주기로 충분하지 않다는 요청이 생기면 다시 본다.

### 6.2 SDK (PR 5에서 확정)

```ts
const prod = verdict.environment({
  project: "support-bot", environment: "prod",
  refreshMs: 60_000,                       // C11. 기본 60초
  timeoutMs: 2_000,                        // 확인을 기다리는 시간. 기본 2초
  fallback: { intent: intentRubric },      // C13, 선택
  onError: (error) => log.warn(error),     // C12
});

const { rubric, versionId, source } = await prod.rubric("intent");
// source: "server" | "stale" | "fallback"
await prod.refresh();                      // 주기와 관계없이 지금 확인. 성공 여부를 돌려준다
```

읽기 요청은 `GET /v1/projects/:project/environments/:env?include=rubrics`다. 응답에 `ETag`가 붙고, `If-None-Match`로 보내면 바뀐 것이 없을 때 304다.

### 6.3 구현하면서 정한 것 (PR 5, 논의하지 않은 것)

- **`ETag`는 포인터만으로 만든다.** 버전은 바뀌지 않으므로 "어느 rubric이 어느 버전인가"가 같으면 응답도 같다. 바뀐 것이 없는 환경을 확인하는 데는 포인터를 읽는 것으로 끝나고 rubric 문서는 읽지 않는다.
- **실패한 확인은 다음 주기까지 다시 하지 않는다.** 서버가 내려가 있을 때 판정마다 2초씩 기다리지 않게 하기 위해서다. 예외는 돌릴 것이 전혀 없을 때(받은 적도 없고 예비도 없음)로, 이때는 호출마다 다시 묻는다.
- **동시에 들어온 호출은 확인 한 번을 같이 기다린다.**
- **환경에 그 rubric의 포인터가 없을 때**: 예비가 있으면 예비를 쓴다(`source: "fallback"`). 처음 승격하기 전에 서비스를 먼저 배포하는 경우를 위해서다. 예비가 없으면 `not_promoted` 오류다. 포인터를 내리는 것(§5.1)은 예비가 있는 서비스를 멈추는 방법이 아니다.
- **예비 rubric도 고정해서 버전 id를 돌려준다.** 예비로 돌린 판정도 어느 버전이었는지 로그에 남는다.
- **확인 실패로 치는 것**: 연결 실패, 제한 시간 초과, 서버의 거절(401·403·404·5xx), 받은 문서가 서버가 말한 id로 고정되지 않음. 모두 `onError`로 알리고 받아 둔 버전으로 진행한다.
- **서버가 문서를 읽는 사이 포인터가 바뀌면** 503으로 답하고, SDK는 이것도 확인 실패로 처리한다.
- **SDK는 rubric을 고정하는 코드(`@verdict-ai/core`)를 처음 환경을 읽을 때 불러온다.** 환경 읽기를 쓰지 않는 SDK 사용자는 그 코드를 싣지 않는다.
- **특정 버전 읽기**는 기존의 `versions.get(project, name, "rv_…")`이다. 따로 만들지 않았다.
- **예제**: `examples/control-plane`. 모델 키 없이 돌도록 키워드로 판정하는 rubric을 쓴다. 서버 → CI 보고 → 승격 → 서비스 → 비교 보고 → 재승격 → 되돌리기를 한 스크립트로 돌리고, 테스트가 이 스크립트를 실행한다.

## 7. 실행 요약 보고 (C14–C16)

### 7.1 실행 요약에 담는 것

| 묶음 | 내용 | 근거 |
| --- | --- | --- |
| 실행 | 실행 id, 버전 id, 데이터셋 버전 id, 상태(완료·일부·실패), 시작 시각 | `PublicRunSummary`와 같다 |
| 조건 지문 | 판단·정책·바인딩 해시, 보낸 질문의 해시, 사례 해시, 레이블 해시, 응답한 모델, 채점 규칙 버전 | 같다 |
| 건수 | 사례 수, 완료, 사람 대기, 실패, 입력 오류, 레이블 있는 사례 수 | 같다 |
| 일치 | 판정한 건수와 일치 수, 기준별·분할별 일치, 레이블 출처 분포 | 같다 |
| 출처(C15) | 커밋, 브랜치, CI 실행 링크. 선택 | 새로 추가 |
| 데이터셋 이름(C15) | 사례 파일 이름(`DatasetVersion.name`) | 새로 추가 |
| 사용량(C15) | decision 호출 수, LLM 호출 수, 입력·출력 토큰 수(`Run.usage`) | 새로 추가 |

- **보내지 않는 것**: 사례 id, 평가 id, 입력, 모델 출력, 근거 문장. 공개 발행 요청은 "모든 사례가 공개인지"를 계산하려고 사례 id 목록을 받지만, 이 보고는 받지 않는다. 서버의 요청 형식에 그 필드가 없다.
- **출처 표시**: 서버는 실행을 다시 돌릴 수 없으므로 모든 요약은 `author_reported`다(revenue.md §4).
- **서버가 확인하는 것**: 요약의 버전이 서버에 있거나 요청에 함께 왔는지(C6, C14), 요약에 적힌 판단·정책·바인딩 해시가 그 버전의 해시와 같은지. 다르면 거절한다.
- **중복**: 같은 실행 id를 다시 보고하면 저장된 것을 돌려준다. CI 재시도에 안전하다.
- **고치기·지우기**: 없다. 프로젝트를 지우면 함께 지워진다. 보관 기간은 이력과 같이 클라우드의 플랜 규칙이 정한다(§5.2).
- **`--mock` 실행은 보고하지 않는다.** CLI가 거절한다. 가짜 모델로 바꾼 rubric은 바인딩이 달라 다른 버전이 되므로, 서버의 버전 목록에도 섞이지 않는다.
- 일부 사례가 실패한 실행도 받는다. 상태와 실패 건수가 그대로 보인다.

### 7.2 비교 요약에 담는 것 (C16)

`compareRuns`(`core/src/versions/compare.ts`)의 결과에서 사례별 행(`cases`)을 뺀 것이다.

- 비교 종류: rubric의 질문만 바뀜(`rubric_change`) · 답을 읽는 방식만 바뀜(`policy_change`. 기준 실행의 답을 다시 읽은 것이라 판정 호출이 없다) · 조건이 같음 · 조건이 다름.
- 조건 차이: 달라진 지문 필드와 양쪽 값(해시, 모델 이름).
- 레이블: 비교에 쓴 데이터셋 버전 id와 레이블 해시, 재채점 여부.
- 기준별: 분류별 건수(유지·수정·회귀·사람에게 넘김·오류·누락 등), 경계 근접 건수, 양쪽 일치율과 분모.
- 양쪽 실행 id와 버전 id. 두 실행의 요약이 먼저 서버에 있어야 한다. CLI는 실행 요약 둘을 보고한 뒤 비교 요약을 보낸다(PR 3에서 "같은 요청에 함께"를 뺐다. 요청 형식이 하나로 줄어든다).

### 7.3 명령

- `verdict report <run_…>`: 저장된 실행의 요약을 보고한다.
- `verdict run … --report`, `verdict diff … --report`: 실행하고 바로 보고한다. `diff --report`는 양쪽 실행 요약과 비교 요약을 보낸다.
- `actions/diff`에 보고 여부 입력을 더한다.

### 7.4 REST (PR 3에서 확정)

| Method | Path | 목적 |
| --- | --- | --- |
| `POST` | `/v1/projects/:project/reports/runs` | 실행 요약 보고. 본문 `{ name, run, report, datasetName?, source?, version? }`. 버전이 서버에 없으면 `version`에 함께 담는다. 새로 저장하면 201, 이미 있으면 200. 버전이 없으면 400(`unknown_version`) |
| `GET` | `/v1/projects/:project/reports/runs?name=&versionId=&dataset=&limit=` | 실행 요약 목록, 최신순 |
| `GET` | `/v1/projects/:project/reports/runs/:runId` | 실행 요약 하나 |
| `POST` | `/v1/projects/:project/reports/comparisons` | 비교 요약 보고. 본문 `{ name, comparison, source? }`. 두 실행이 보고되어 있지 않으면 400(`unknown_run`) |
| `GET` | `/v1/projects/:project/reports/comparisons?name=&head=&limit=` | 비교 요약 목록 |

### 7.5 구현하면서 정한 것 (PR 3, 논의하지 않은 것)

- **사례가 나가지 않게 하는 방법**: 요청 형식에 사례 id·평가 id·입력·출력을 담을 필드가 없다. 서버는 모르는 필드를 버린다. CLI는 요청을 만드는 함수 하나(`runReportRequest`, `comparisonReportRequest`)만 쓰고, 이 함수는 실행의 조건과 건수를 필드 하나씩 옮긴다. 서버 테스트와 CLI 테스트가 비공개 사례의 이름·전화번호·사례 id가 어떤 요청에도 없는지 확인한다.
- **버전은 보고에 항상 함께 보낸다.** CLI가 서버에 버전이 있는지 먼저 묻지 않는다. 요청이 하나로 끝나고, 서버에 이미 있으면 저장된 것을 그대로 쓴다.
- **허용 여부는 보고마다 한 번 묻는다**(`report.put`). 함께 온 버전을 저장하는 것은 이 허용에 포함된다(C14). 같은 키가 버전만 따로 올리는 것(`version.put`)은 별개로 묻는다.
- **비교 요약의 id는 내용에서 정한다.** 같은 두 실행을 같은 레이블로 비교한 것은 같은 비교다. 다시 보고하면 저장된 것을 돌려준다.
- **rubric 이름(C2)을 정하는 순서**: `--name`, `verdict.lock`의 `name`, rubric의 `id`, 파일 이름. `id`와 파일 이름은 소문자·숫자·`-`로 바꿔 쓴다(`Agent_Intent` → `agent-intent`). `diff --report`는 head의 이름을 양쪽 실행에 쓴다. 실행 id만 주는 `verdict report run_…`은 lock에서 그 버전의 파일을 찾고, 없으면 `--name`을 요구한다. lock에 `name`을 적는 것은 `push`와 `promote`다(PR 4).
- **출처(C15)의 기본값**: GitHub Actions가 주는 값(`GITHUB_SHA`, `GITHUB_HEAD_REF` 또는 `GITHUB_REF_NAME`, 실행 링크)을 쓴다. `--commit`, `--branch`, `--run-url`로 바꾼다. CI 밖에서는 비어 있다.
- **프로젝트와 서버**: `--project` 또는 `VERDICT_PROJECT`, 서버와 키는 허브 설정(C17). `verdict.yaml`도 읽는다(PR 4, §8.1).
- **보고는 실행하기 전에 확인한다.** 프로젝트가 없거나 `--mock`이면 판정 모델을 부르기 전에 멈춘다. mock 공급자로 만든 저장된 실행도 거절한다.
- **`diff --report`는 게이트보다 먼저 보고한다.** 회귀가 있어 실패하는 비교가 서버에서 가장 보여야 하는 비교다.
- **액션(`actions/diff`)에서 보고 실패는 job을 실패시키지 않는다.** 댓글과 경고에 이유를 남긴다. 게이트는 rubric에 대한 것이고 서버 상태에 대한 것이 아니다. CLI를 직접 쓰는 `--report`는 보고에 실패하면 0이 아닌 값으로 끝난다. 댓글에는 서버 주소를 적지 않는다(공개 저장소의 댓글일 수 있다).
- **새 rubric(기준 버전 없음)**: 액션은 비교할 것이 없어 보고하지 않는다. 필요하면 `verdict run --report`를 따로 쓴다.

## 8. CLI 설정과 명령 (C17–C19)

### 8.1 설정

- **읽는 순서**: 명령의 옵션, 환경 변수, `verdict.yaml`, 저장된 로그인.
- **서버 주소(C17)**: `--hub <url>`, `VERDICT_HUB_URL`, `verdict.yaml`의 `server`, 가장 최근에 로그인한 서버 순으로 정한다. `verdict.yaml`의 `server`는 관리 명령(§8.2)에만 적용한다. 발행·`pull`·`fork hub:`는 지금의 순서를 그대로 쓴다. 클라우드에서는 둘이 같은 주소다(R7).
- **키**: `VERDICT_HUB_KEY`, 없으면 그 주소로 저장된 로그인. 로그인 파일(`~/.config/verdict/hub.json`)은 주소별로 키를 보관한다. 지금 형식(서버 하나)의 파일도 계속 읽는다.
- **`VERDICT_API_URL`은 관여하지 않는다.** 이 값은 평가를 원격 서버에서 실행하게 하는 설정이고, 관리 명령은 실행을 로컬에 둔 채 숫자만 보낸다(R2).
- **`verdict.yaml`(C18)**: 현재 디렉터리에서 위로 올라가며 찾는다.

```yaml
project: support-bot
server: https://verdict.example.com   # 선택
```

- **rubric 이름**: 처음 올릴 때 정한 이름(C2)을 `verdict.lock`의 그 파일 항목에 `name`으로 적는다. 이후 명령은 그 이름을 쓴다. 파일을 옮기거나 파일 이름을 바꿔도 서비스가 읽는 이름은 그대로다.

### 8.2 명령

| 명령 | 하는 일 |
| --- | --- |
| `verdict login` | `verdict hub login`과 같다(C17) |
| `verdict project create\|list\|delete` | 프로젝트 관리(C3) |
| `verdict env create\|list\|show\|delete` | 환경 관리, 포인터 보기 |
| `verdict env history` | 승격 이력(§5.2) |
| `verdict env unset <이름> --env prod` | 포인터 내리기 |
| `verdict push <파일\|rv_…>` | 버전 올리기(C6) |
| `verdict promote <파일\|rv_…>… --env prod` | 승격. `--from staging`, `--note`, `--yes` |
| `verdict rollback <이름> --env prod` | 되돌리기(C9) |
| `verdict report <run_…>` | 실행 요약 보고. `run --report`, `diff --report`도 있다(§7.3) |

구현(PR 4)에서 더한 옵션: `verdict login --with-key`, `verdict hub logout --hub <주소>`, `verdict promote`의 `--name`(참조가 하나일 때), 모든 변경 명령의 `--yes`와 `--json`.

### 8.3 승격 전 검사 (C19)

- 파일을 지정한 승격: 파일을 고정한 id가 `verdict.lock`의 `version`과 다르면 거절하고 `verdict version freeze`를 안내한다. lock에 그 파일이 없을 때도 같다.
- `rv_…`를 지정한 승격과 `--from`: 파일이 없으므로 이 검사는 하지 않는다.
- 모든 승격: 그 버전의 실행 요약이 서버에 없으면 경고하고 진행한다.
- 그다음 현재 포인터와 바뀔 내용을 보여주고 확인을 묻는다(§5.1).

### 8.4 MCP

M1a에는 MCP 도구를 넣지 않는다. 에이전트가 혼자 운영 환경을 승격하는 경로를 열지 않기 위해서다. 읽기 전용 도구는 요청이 있으면 추가한다.

### 8.5 구현하면서 정한 것 (PR 4, 논의하지 않은 것)

- **자체 호스팅 서버의 키 보관**: GitHub 로그인이 없는 서버는 `verdict login --hub <주소> --with-key`로 운영자가 준 키를 저장한다. 키는 표준 입력으로 받는다(명령줄 인자로 받으면 셸 기록에 남는다). 저장 전에 서버에 한 번 확인하고, 서버가 거절한 키는 저장하지 않는다.
- **로그인 파일 형식**: 주소별 키는 `servers` 아래에 둔다. 파일의 맨 위에는 가장 최근 로그인을 예전 형식 그대로 둔다. 예전 CLI가 같은 파일을 읽어도 최근 로그인으로 동작한다.
- **`verdict.yaml`은 가장 가까운 파일 하나만 읽는다.** 위쪽 디렉터리의 파일과 합치지 않는다. 하위 디렉터리에 다른 프로젝트를 둘 때 값이 섞이지 않게 하기 위해서다.
- **빈 환경 변수는 없는 것으로 본다**(`VERDICT_HUB_URL=""` 등). CI에서 값이 빈 채로 넘어오는 경우가 흔하다.
- **승격은 확인을 받은 뒤에 버전을 올린다.** "아니오"라고 답하면 서버에 아무것도 남지 않는다.
- **이름을 lock에 적는 조건**: 그 파일이 lock에 고정되어 있을 때만 적는다. 버전 없이 이름만 있는 항목은 `verdict version verify`를 실패시키기 때문이다. 고정하지 않은 파일을 `--name`과 함께 올리면 이름이 기록되지 않는다고 알린다.
- **`rv_…`로 승격할 때의 이름**: 이 컴퓨터에 그 버전이 있으면 lock에서 그 버전의 파일을 찾아 이름을 정한다. 없으면 `--name`이 필요하고, 서버가 그 이름 아래 가진 버전을 쓴다.
- **`--from`과 함께 적는 것은 rubric 이름이다.** 적지 않으면 그 환경이 가리키는 것 전부를 승격한다.
- **이미 같은 버전이면 건너뛴다.** 건너뛴 rubric은 한 줄로 알리고, 바뀔 것이 없으면 서버에 요청하지 않는다(§5.4).
- **되돌리기의 미리 보기**는 이력의 가장 최근 변경에서 읽는다. 실제로 어디로 돌아갈지는 서버가 정한다.
- **`push`, `promote`, `rollback`은 `VERDICT_API_URL`이 설정되어 있어도 동작한다**(§8.1). `report`와 `--report`는 저장된 실행을 읽어야 하므로 로컬 엔진이 필요하다.
- **최상위 별칭은 `verdict login`만 만들었다**(C17). `logout`, `whoami`는 `verdict hub` 아래에 있다.

## 9. 공개 코드와 비공개 코드가 만나는 자리 (C20–C21)

M1a는 공개 저장소에 만들고 API 키 하나가 모든 일을 한다. M1b부터 비공개 저장소가 공개 API 앱을 가져와 사람, 역할, 한도를 얹는다(R8, revenue.md §7). 비공개 코드가 공개 코드를 복사하거나 고치지 않도록 아래 두 자리를 M1a에서 만든다.

### 9.1 허용 여부를 묻는 자리 (C20)

- **주체**: 지금 인증(`Auth.resolve`)은 키에서 계정(tenant)만 알아낸다. 이것을 "계정 + 요청한 주체(종류, id, 이름)"를 돌려주도록 넓힌다. M1a에서 주체는 API 키다. M1b에서 비공개 코드가 사람으로 바꿔 넣는다. 계정만 돌려주는 기존 구현(`envAuth`)은 그대로 동작하고, 그때 주체는 이름 없는 키다.
- **묻는 내용**: 주체, 동작, 대상(프로젝트, 환경, rubric 이름).
- **동작 목록**: 프로젝트 만들기·삭제·읽기, 환경 만들기·삭제·읽기, 버전 올리기·읽기·삭제, 포인터 승격·되돌리기·내리기, 이력 읽기, 보고 올리기·읽기.
- **답**: 허용, 또는 거절과 이유. 이유는 구분할 수 있는 값이다(권한 없음, 한도 초과, 승인 필요). 화면과 CLI가 이 값으로 안내문을 고른다(§3.3).
- **기본값**: 공개 저장소에서는 항상 허용이다. 자체 호스팅은 제한 없이 동작한다(revenue.md §3.1).
- **빠뜨림 방지**: "전부 거절"로 설정한 앱에서 `/v1/projects` 아래의 모든 경로가 거절되는지 테스트한다. 이 자리를 거치지 않는 경로가 생기면 테스트가 실패한다.
- **이력의 "누가"**(§5.2)는 주체를 그대로 적는다.
- 웹 로그인으로 들어온 요청도 같은 자리를 지난다. 주체를 만드는 방법만 다르다.
- **구현(PR 2)**: `createApp({ authorize })`. 경로는 저장소를 읽거나 쓰기 전에 먼저 묻는다. 테스트는 `/v1/projects` 아래 경로를 앱에서 직접 나열하고, 사용하면 실패하는 저장소를 붙여 모든 경로가 403인지 확인한다. DB에 저장한 키(`DrizzleAuth`)는 키의 id와 이름을 주체로 돌려준다. 환경 변수로 준 키(`envAuth`)는 이름 없는 키다.

클라우드가 이 자리에서 할 일(비공개 저장소, 참고):

| 요청 | 답 | 근거 |
| --- | --- | --- |
| CI 키의 승격·되돌리기·버전 삭제 | 거절(권한 없음) | R5, C14 |
| 무료 조직의 두 번째 환경 만들기 | 거절(한도 초과) | R9 |
| 구독이 끝난 조직의 읽기 전용 환경에 승격 | 거절(한도 초과) | R15 |
| 승인 조건이 걸린 환경에 승격 | 거절(승인 필요). 승인이 끝나면 비공개 코드가 승격을 수행한다 | R13, M2a |
| 서비스가 환경 포인터를 읽기 | 플랜과 결제 상태에 관계없이 허용 | revenue.md §3.4 |

### 9.2 경로 묶음 (C21)

- 앱을 만들 때(`createApp`) 켤 경로 묶음을 고른다: 평가 실행(`/v1/evaluations`, `/v1/batches`), 수정 가능한 rubric(`/v1/rubrics`), 허브(`/v1/hub`, `/v1/publications`, `/v1/public`), 관리(`/v1/projects`). 기본은 전부 켬이다.
- 클라우드는 허브와 관리만 켠다. 끈 경로는 404다.
- 지금 코드는 허브에 로그인해 받은 키로 평가 실행 경로를 부를 수 있다. 클라우드 빌드에서 이 묶음을 꺼서 닫는다.
- **구현(PR 2)**: `createApp({ routes: ["hub", "control"] })`. 묶음 이름은 `evaluations`, `rubrics`, `hub`, `control`이다. 끈 묶음의 경로는 `/v1/openapi.json`에서도 빠진다. 관리자 경로(`/v1/admin`)와 상태 확인 경로는 항상 켜져 있다. 함께 배포하는 서버(Node, Workers)는 환경 변수 `VERDICT_ROUTES="hub,control"`로 같은 선택을 한다.
- **M1b 전에 알아 둘 것**: 기본값이 전부 켬이므로, 지금 공개 허브를 `main`으로 다시 배포하면 GitHub로 로그인한 누구나 `/v1/projects`에 프로젝트와 버전을 만들 수 있다. 한도는 M1b에 생긴다. 그 전에는 허브 배포에 `VERDICT_ROUTES`로 `control`을 꺼 둔다.

### 9.3 DB

공개 저장소에 아래 표를 만든다. 문서는 JSON 열에 두고, 조회에 쓰는 값만 열로 뺀다(AGENTS.md). SQLite와 Postgres 마이그레이션을 함께 낸다.

| 표 | 키 | 담는 것 |
| --- | --- | --- |
| 프로젝트 | 계정 + 이름 | 이름, 만든 시각 |
| 환경 | 계정 + 프로젝트 + 이름 | 이름, 만든 시각 |
| 버전 | 계정 + 프로젝트 + rubric 이름 + 버전 id | rubric 문서, 해시, 부모 정보 |
| 포인터 | 계정 + 프로젝트 + 환경 + rubric 이름 | 가리키는 버전 id, 바뀐 시각 |
| 승격 이력 | 이력 id | 환경, rubric 이름, 이전·새 버전, 종류, 메모, 주체, 시각 |
| 실행 요약 | 계정 + 프로젝트 + 실행 id | 요약 문서. 열: rubric 이름, 버전 id, 데이터셋 이름, 시작 시각 |
| 비교 요약 | 비교 id | 요약 문서. 열: rubric 이름, 양쪽 실행 id, head 버전 id |

- **공개 읽기 경로는 만들지 않는다.** 새 표는 전부 계정 범위로만 읽는다. 인증 없이 읽는 것은 지금처럼 `publications`뿐이다(AGENTS.md, revenue.md §6).
- **계정이 없는 서버**: 키 없이 여는 단일 계정 서버에서는 계정 값이 비어 있다. 키에 계정이 들어가므로 빈 값을 NULL이 아니라 빈 문자열로 저장한다. NULL은 중복 검사에서 서로 다른 값으로 취급된다.
- **한 묶음으로 처리하는 방법(PR 1 구현)**: D1에는 대화형 트랜잭션이 없고 여러 문장을 한꺼번에 보내는 배치만 있다. 그래서 C8의 "현재 상태 확인"과 C4의 "전부 적용하거나 전부 거절"을 문장 안의 조건으로 넣었다. 이력 줄은 "환경이 있고, 모든 포인터가 요청이 본 버전에 있고, 대상 버전이 그 이름 아래 있을 때만" 들어가고, 포인터 변경은 자기 이력 줄이 들어갔을 때만 일어난다. 배치가 끝난 뒤 이력 줄이 있는지 읽어서 적용 여부를 안다. 버전 삭제(C7)도 "가리키는 포인터가 없을 때만"을 문장 안에 넣었다. Postgres에서는 같은 문장을 트랜잭션과 프로젝트별 잠금으로 실행한다.
- **한 요청의 변경 수 제한**: D1은 문장 하나에 값 100개까지만 받는다. 위 조건이 변경 하나마다 값을 쓰므로 한 요청에 담는 변경은 rubric 20개까지다(`CONTROL_MAX_CHANGES`).
- **로컬 D1에서 확인한 것**(2026-11-10): Cloudflare의 실행기(workerd)가 내는 D1 API 위에서 실제 마이그레이션을 적용하고 공통 테스트 전부, 변경 20개짜리 승격, 평가 저장, 키 인증을 돌린다(`packages/db/test/d1.test.ts`). 배포한 Worker가 지나는 길(`fromD1`)과 같다. 네트워크와 계정 없이 돈다.
- **배포한 D1에서 확인한 것**(2026-11-10): 실제 배포에서 마이그레이션 적용과 예제 흐름 전체(§10).
- **아직 확인하지 못한 것**: 운영 중인 D1 서비스가 강제하는 한도에 닿는 경우(문장당 값 100개: 변경 20개짜리 승격). 값의 개수는 테스트가 따로 센다(`control.test.ts`).
- 조직, 멤버, 좌석 표는 비공개 저장소가 같은 DB에 따로 둔다(R7).

### 9.4 감수하는 것과 M1b로 넘기는 것

- **감수하는 것**: 자체 호스팅에는 읽기 전용 키가 없다. 서비스에 넣는 키로 승격도 할 수 있다. 키 권한 제한은 클라우드 기능이다(R5, R8).
- **M1b에서 정할 것**: 허브 로그인은 지금 GitHub 계정 하나를 계정(tenant) 하나로 만든다(hub.md §16.2). 이것을 "조직에 속한 사람"으로 바꾸는 방법, 역할별 허용 표, 한도 검사, 웹 화면의 구성(C22–C24).

## 11. 어느 컴퓨터에서든 서버의 버전으로 (C25–C28) **[결정]** (2026-11-11)

**왜 다시 정했나.** C5는 "원본은 저장소의 rubric 파일 하나"라고 했다. 그 결과 한 컴퓨터에서 쓰던 rubric을 다른 컴퓨터에서 쓰려면 git으로 파일을 옮겨야 했다. 서버는 올라온 버전의 문서 전체를 이미 갖고 있고 서비스는 SDK로 그것을 받아 쓰는데(§6), CLI만 로컬 파일을 요구했다. 비밀 값 관리 도구들(한 번 저장하면 어느 컴퓨터에서든 로그인해 받아 쓴다)처럼 쓰게 한다.

| # | 결정 | 고려한 다른 선택지와 비용 |
| --- | --- | --- |
| **C25** | **원본은 서버의 버전이다.** 어느 컴퓨터든 로그인하면 이름으로 받아 쓴다. rubric 파일은 새 버전을 만들 때만 필요하고, 저장소에 커밋하는 것은 선택이다. C5의 "원본은 저장소의 rubric 파일 하나다"를 이것으로 바꾼다. C5의 나머지(고정한 것을 그대로 올린다, 서버가 id를 다시 계산한다)는 그대로다 | 파일이 원본인 채로 내려받는 명령만 더하면 고칠 결정이 없지만, "git으로 공유하라"가 계속 기본이라 저장소를 함께 쓰지 않는 사람은 rubric을 쓸 수 없다. 버전은 내용에서 id가 나오므로 서버의 것과 파일의 것이 "어긋나는" 일은 없다: 같으면 같은 id이고 다르면 다른 버전이다 |
| **C26** | rubric을 받는 명령은 **파일 대신 서버의 이름**도 받는다: `intent`와 `--env prod`(그 환경이 돌리는 버전), `intent@latest`(가장 최근에 올라온 버전), `intent@rv_…`(그 버전). `run`, `diff`, `eval`, `check`, `compare`가 받는다. 파일은 생기지 않는다. 받은 문서는 그 자리에서 다시 고정해 서버가 말한 id와 같을 때만 쓰고, 로컬 데이터 폴더에 보관한다 | 항상 먼저 파일로 내려받게 하면 만들 것은 적지만 컴퓨터마다 파일이 흩어지고 낡는다 |
| **C27** | 작업 중인 rubric을 다른 컴퓨터와 나누는 방법도 **버전 하나를 올리는 것**이다. `verdict push <파일>`이 고정하고 lock에 적는 일까지 한 번에 한다. 받는 쪽은 `@latest`나 id로 받는다 | 서버에 덮어쓸 수 있는 "초안"을 따로 두면 더 가볍게 나눌 수 있지만, 새 표와 API가 필요하고 "같은 id는 같은 문서"에 예외가 생긴다 |
| **C28** | 고치려는 사람을 위해 **파일로 내려받는 명령**을 둔다: `verdict pull intent --env prod`(또는 `@latest`, `@rv_…`). 쓴 파일이 같은 id로 고정되는지 확인한 뒤에 쓰고, lock에 버전과 서버에서의 이름을 적는다. 허브 카드를 받는 `verdict pull hub:…`와 같은 명령이다 | 내려받기를 두지 않으면 고치려는 사람은 웹 화면에서 문서를 복사해야 한다 |

모델 키는 서버가 보관하지 않는다. 평가는 받은 컴퓨터에서 그 컴퓨터의 키로 한다. 이것은 바뀌지 않았다(§6, R5).

### 11.1 규칙

- **이름으로 읽는 조건**: `@`가 붙었거나 `--env`가 있을 때만 서버의 이름으로 읽는다. 그렇지 않은 이름은 지금까지의 뜻 그대로다(`eval -r <저장된 rubric id>`). `--env`는 파일이나 `rv_…`의 뜻을 바꾸지 않는다. `@`와 `--env`를 함께 쓰면 거절한다.
- **어디에 묻나**: 프로젝트와 서버는 관리 명령과 같은 순서로 정한다(§8.1): 옵션, 환경변수, `verdict.yaml`, 마지막 로그인.
- **무결성**: 받은 문서를 다시 고정한 id가 서버가 말한 id와 다르면 쓰지 않고 보관하지도 않는다(§4.1의 "내려받기"와 같다).
- **서버에 묻지 않는 경우**: `intent@rv_…`가 이미 이 컴퓨터에 있으면 로그인도 통신도 없이 쓴다. 버전은 바뀌지 않기 때문이다. `--env`와 `@latest`는 "지금 무엇인가"를 묻는 것이라 서버가 필요하고, 닿지 않으면 id로 쓰는 방법을 알려 주고 멈춘다. (서비스의 SDK는 닿지 않아도 가진 버전으로 계속 답한다. 사람이 치는 명령은 무엇이 도는지 모른 채 돌리지 않는다.)
- **`--env`는 읽기 전용 키로도 된다**: 환경과 문서를 한 번에 주는 기존 경로(`?include=rubrics`, §6)를 쓴다. `@latest`와 `@rv_…`는 버전을 읽는 권한이 필요하다.
- **무엇을 썼는지 말한다**: 명령마다 한 줄을 stderr로 낸다. 예: `intent: rv_…, what prod runs in support-bot on https://…`.
- **보고의 이름**: 이름으로 받은 버전의 실행을 보고하면(`--report`) 그 이름으로 보고한다.
- **`push`와 lock**: 파일을 올리면 lock의 버전이 올린 버전이 된다. 그래서 `push` 다음의 `promote <파일>`은 `version freeze` 없이 통과한다(C19의 "lock이 말하는 버전만 승격한다"는 그대로다. lock에 적는 길이 하나 늘었다).
- **`pull`과 부모**: 내려받은 파일의 lock에는 부모를 적지 않는다(허브에서 받을 때와 같다). 고친 버전에 부모를 남기려면 `verdict fork rv_… --to <파일>`을 쓴다.

### 11.2 바뀐 것

- CLI: `packages/cli/src/control/server-ref.ts`(이름 읽기, 받기, 확인), `run`·`diff`·`eval`·`check`·`compare`의 `--env`와 서버 옵션, `pull`의 프로젝트 내려받기, `push`의 lock 기록.
- SDK: `environments.get(project, name, { include: "rubrics" })`. REST는 바뀌지 않았다.
- CLI의 문장과 문서에서 "organisation"을 "organization"으로 고쳤다.

### 11.3 확인한 것과 못 한 것

- 테스트: 컴퓨터 둘이 한 서버를 쓰는 흐름(올리기 → 승격 → 다른 컴퓨터에서 파일 없이 실행·평가·비교 → 내려받아 고쳐 올리기 → 처음 컴퓨터가 이름으로 받기), 이미 가진 버전은 통신 없이 쓰는 것, 서버가 다른 문서를 보내면 쓰지 않는 것, 거절 문장들.
- 실제로 해 본 것(2026-11-11): 빌드한 CLI와 `verdict serve`로 폴더 둘을 컴퓨터 둘로 삼아 같은 흐름을 돌렸다. 서버를 끈 뒤 id로는 실행되고 `--env`로는 안내와 함께 멈췄다.
- 못 한 것: 호스팅 서비스(로그인한 사람의 키, 읽기 전용 키)에서의 실행.
